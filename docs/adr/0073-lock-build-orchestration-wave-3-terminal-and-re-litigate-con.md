# Lock `build-orchestration` (Wave 3, terminal) and re-litigate `control-plane` to add the gated **Review** PR-contract section

*Decided 2026-05-26 in the design workspace.*

## The decision

Two coupled ratifications under one decision (the [D-049](0049-re-lock-topology-and-module-system-file-precise-codeowners-o.md) precedent). Lock [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) to its end-state — the **terminal Wave-3 lock** — and, because that end-state needs a gated home for the build's review record, **re-litigate the locked [control-plane](../spec/systems/infrastructure/control-plane.md)** ([D-017](0017-control-plane-locked-end-state-as-contracts-not-leaves.md)) under the litigation-alarm protocol (operator-approved) to add a required **Review** section to the PR contract. **build-orchestration's fixed laws:** (1) **Two surfaces** — the draft PR is the change/claim/close surface; the **build Issue (a Milestone's machine-readable decomposition) is the forward-plan surface**, an ordered commit-sequence checklist authored at Plan, operationalizing locked [state](../spec/systems/cognitive/state.md) ("Milestones are the plan; open Issues are backlog") without expanding it and never a committed work-inventory; the resume it gives an unattended session is **bounded by GitHub availability** (offline ⇒ no plan ⇒ fail-safe no-op). (2) **Fixed gate shape, derived lenses, posture tier** — the skeleton (Plan → plan-review → implement → integrate → pre-submission → submit) is the orchestrator's *workflow*; nothing mechanically forces the lenses before the merge; the only wall is the protected-branch merge; the one mechanical hook is the PR **Review** section's presence. (3) **The plan gate runs in two beats** — a risk-assessment **consent before the spend** (a varying plain-language headline + a **consequence-named depth** choice + a cost estimate, operator-gated; the operator never sees lens slugs) and, **after the audit**, the orchestrator's synthesis of the lens findings into one recommended call plus the trade, re-engaging the operator on material findings and **always on an unresolved `blocking` finding**, every disposition surfaced. (4) **The orchestrator is the single writer** — workers (a cheaper persona tier, [D-057](0057-lock-the-agents-surface-wave-1-four-settled-design-forks.md)) generate mechanical work product in isolated worktrees; the orchestrator **reviews → revises → authors** the cohesive set; delegation buys **cohesion under context pressure**, not speed, and reconciling semantic overlap is real bounded work; partial failure is a missing planned commit, not a phantom slot. (5) **Validate before the expensive review; rerun validation, not the audit** — a green baseline gates pre-submission; validation reruns on every change, the cold audits run once at agreed depth and don't rerun on fixes unless the operator asks, the Review record stating that delta. (6) **A real proportionality floor** — the fast path is the operator-typed Build entry + one headline + one merge; "fixed gates" is a shape, never a fixed depth. (7) **Routine** is the same workflow distributed across unattended **Local Desktop** sessions for **decomposable bulk work only** (a Plan-time judgment, not enforced): the plan + scope-lock live in the build Issue; sessions run in a **non-interactive permission posture** so they genuinely *cannot ask* rather than stall; single-flight is the **Desktop scheduler's skip-while-running** behavior (the local counterpart to control-plane's Actions single-flight law); cohesion is planned-up-front + checked-at-Finalize; never auto-merges. A **Build-spec leaves** section holds the checklist+scope-lock format, the non-interactive posture, the depth-level grammar, the Review-section layout, the risk-assessment wording, and the worker-worktree base note; a [§12](../principles.md) leak guard fences the maintainer vocabulary and the honest tier is **surfaced to the operator** at merge. **control-plane re-litigation:** the PR contract's required-section list gains **Review** (`Purpose · Scope · Out of scope · Risk · Validation · Review · Files of interest · Claude involvement`) — the **judgment-layer** record of what review a change received (depth, lenses run, gate completion, dispositions, post-audit-fix delta), distinct from the mechanical **Validation** section and from **Claude involvement**, bound by the existing PR-body completeness check at the **same honest tier as its siblings** (**presence and non-emptiness hard-gated; truthfulness posture**), operator-read in plain language and stating in-block that it is the engine's own account and the operator's merge is the real gate; it is the **one** section whose subject the operator cannot independently corroborate, so its posture tier is load-bearing. No other locked doc changes: [validation](../spec/systems/guardrails/validation.md) locks the *check mechanism*, not the section list; the seam stays *control-plane locks the contract, build-orchestration fills Review at submit, validation implements the check*. **lifecycle decomposition** (the catalog/WBS deferred it here): `session-lifecycle` and `build-readiness-gate` (both bare stubs) are **folded into `core`** — the build orchestration workflow and its plan-review gate are core — and **deleted**; `routine-mode` (the routine stance) now depends on `core`. `python3 lock.py --relock systems/infrastructure/control-plane/README.md --decision D-073` then `python3 lock.py systems/lifecycle/build-orchestration/README.md --decision D-073`; ratified_by D-073.

## Why

build-orchestration is the last `designed` lifecycle system and the correct terminal Wave-3 lock: its upstream anchors (modes, close, control-plane, state, agents, boot) are all locked and the `designed` things it consumes (the design-review/qa-review suites, product-design) are downstream and settled by [D-065](0065-product-design-front-door-design-the-q14-intake-module-as-a.md)/[D-066](0066-the-4-4-review-lens-roster-two-stage-suites-mirroring-the-en.md)/[D-067](0067-operator-facing-module-packaging-industry-discipline-categor.md)/[D-068](0068-q1-resolved-the-v1-optional-module-roster-4-cut-2-kept.md) via pure deferral (it names the rosters and the referent, fixing neither). A working dialog reshaped five points (forward-plan home; the two-beat plan gate; the worker model as cohesion-not-speed; fail-fast validate-before-audit; the routine purpose), and **two four-lens cold-session design audits** ([D-018](0018-cold-session-design-audit-required-before-any-lock.md)) then ran — one on the build-orchestration plan, one focused on the control-plane Review delta — each materially reshaping the result, not just wording. The build-orchestration audit caught two blockers: the **routine scope-lock had no durable cold-readable home** (→ placed in the build Issue with the checklist), and **"materially impactful" let the orchestrator silently swallow a `blocking` finding** (→ the always-re-engage floor + every disposition surfaced); plus serious findings reframed honestly — the gate skeleton is **posture** not "fixed/always-runs"; "cannot ask" is **only true under a non-interactive posture** (else a Desktop run *stalls*, technical-feasibility verified against the Desktop scheduled-tasks docs); single-flight for Desktop routines is the **scheduler's skip-while-running**, not the Actions concurrency law it had miscited; the depth choice must be **operator-language levels with consequences**, not lens slugs; worker output can **semantically overlap** so reconciliation is real bounded work; and the honest tier must **reach the operator**, not only maintainer prose. The control-plane delta audit returned **no blocking findings** (feasibility confirmed an 8th gated section is trivial for the default token and that fast-path PRs fill it with a minimal truthful line) and drove the Review section's operator-facing honesty rules (the in-block "my own account; your approval is the real gate" caveat, the consequence-named post-audit-fix delta, and the statement that Review is the one uncorroborable section). The re-litigation is **justified, not scope creep**: control-plane's own logic ("the structured PR contract is what makes the merge informed consent"; "structure and presence hard-gated, truthfulness posture") makes a review record the same class of artifact as Risk/Validation, and the operator rejected the easy posture-dodge in favor of doing it properly through the protocol. Propagation per the matrix: control-plane (Review section), build-orchestration (replaced), [scenarios/build-session.md](../architecture.md#build-session-lifecycle) + [scenarios/routine-session.md](../architecture.md#routine-session) (validate-before-pre-submission ordering, commit-sequence, single-writer, Review record, non-interactive routine, Desktop single-flight), [modules/README.md](../reference/module-catalog.md) (stubs folded into core, graph re-cut, routine-mode→core), wbs/README.md (decomposition resolved), [glossary](../reference/glossary.md) (commit-sequence, the two-beat Plan-gate risk assessment, the new Review-record term), [risks.md](../reference/risks.md) R10 (two-beat flow + Review record), the two stub deletions (no GRAVEYARD — the decision-log links neither module path). [R6](../reference/risks.md)/[R10](../reference/risks.md) firmed, not closed; [engine-architecture.md](../architecture.md) verified still truthful (index-only; no "commit graph" survives).

## What we ruled out

Keep the audit record as **posture legibility riding existing sections** without a gated home (rejected — the operator's call: it dodges a locked-doc edit to do the easy thing; a review record belongs in the contract on the same footing as Risk/Validation, and the lock exists to stop *silent* drift, not justified edits). **Fold Review into Validation** (rejected on the rubric, not mere preference — Validation is the *mechanical* layer; folding the *judgment* record into it blurs the very mechanical-vs-judgment line the section exists to sharpen, and a distinct section serves auditability §4). **One Issue per planned commit** (rejected — a checklist in the build Issue is the lighter native form; routine's serial single-flight needs only an ordered sequence). **A single-beat plan gate** synthesizing findings into the pre-approval risk assessment (rejected — the lenses run *after* the depth is approved, so synthesis is post-audit; conflating them was the as-written ambiguity the dialog resolved). **Frame the gate skeleton as "fixed/always runs"** (rejected — nothing forces the lenses pre-merge; the honest tier is posture + the merge wall + the Review-presence hook, matching modes/close). **Frame workers as a speed/parallelism play** (rejected — the load-bearing rationale is cohesion under context pressure; an orchestrator generating 6–10 commits itself drifts, so delegation keeps generation out of its window and lets it author the cohesive set). **Hardcode orchestrator=Opus / worker=Sonnet** (rejected — model-tier is persona-owned, [D-057](0057-lock-the-agents-surface-wave-1-four-settled-design-forks.md); the doc carries only the tier-split *rationale*). **Cite the control-plane Actions concurrency law for Desktop-routine single-flight** (rejected — Actions concurrency cannot serialize a local Desktop session; the scheduler's skip-while-running is the real mechanism). **Treat "cannot ask" as automatic** (rejected — a Desktop run stalls on a permission prompt unless run non-interactively). **Use cloud Routines** (rejected — its fully-autonomous, fresh-clone, `claude/`-branch model does not fit; Local Desktop only). **Present "decomposable bulk work only" as enforced** (rejected — it is a Plan-time orchestrator judgment that redirects coupled work to interactive Build; stated honestly, not a guarantee). **Add a new required check or edit validation** for the Review gate (rejected — the existing completeness check already gates section presence; only control-plane's section list grows). **Migrate [D-051](0051-guardrail-integrity-the-builder-cannot-silently-weaken-its-o.md)'s weakening-change surfacing onto Review** (rejected — D-051's Risk + Claude-involvement surfacing is **undisturbed**; Review is additive, recording that the audit ran, so there is no phantom second home). **Defer the build-orchestration lock or the lifecycle decomposition** (rejected — it is the terminal Wave-3 lock anchored on locked upstreams, and the catalog/WBS explicitly assigned the decomposition to this pass). **Edit any locked doc other than the approved control-plane re-litigation** (rejected — every other reference is a deferral *to* build-orchestration).
