# Lock `github-projects-sync` (the board projection): the eleventh module lock; remediate the Projects-v2 platform-fact errors (Q34)

*Decided 2026-05-30 in the design workspace.*

## The decision

Ratify and **lock** [github-projects-sync](../spec/modules/github-projects-sync.md) (`status: designed → locked`) — the `optional` Product Management module that projects the engine's work-control signal onto a GitHub Project board — the **eleventh module lock**, bringing locks.yaml to **40 docs** (29 systems + 11 modules); only [dependency-discipline](../spec/modules/dependency-discipline.md) ([Q35](../reference/open-questions.md)) remains for all 12 v1 modules locked. It became lock-eligible when [Q34](../reference/open-questions.md) — its sole remaining gate — was remediated: the doc asserted GitHub Projects v2 capabilities that **do not exist**, surfaced by its 2026-05-30 cold audit ([D-144](0144-conclude-the-module-packaging-lock-sweep-six-modules-locked.md)). **Platform facts ground-truthed twice against current GitHub docs** (the proposing session, then again the cold audit's technical-feasibility lens): auto-add is enabled in the **Projects UI only** — **no GraphQL/`gh` mutation enables a built-in workflow** (only `deleteProjectV2Workflow`, plus a readable `ProjectV2Workflow.enabled`); **Status-on-close and Status-on-merge are the two default-enabled** workflows while **auto-add is off by default**; `updateProjectV2ItemFieldValue` writes **per project-item id** and `addProjectV2ItemById` is **idempotent** (returns the existing item); `gh project create`/`link` need the `project` scope; and there is **no API to pin a card**. **Q34 landed as designed-doc edits** (no locked-doc change): split the conflated native layer (Status-on-close/merge default-on/zero-code and act only on items already on the board; auto-add off-by-default and **operator-UI-enabled**, the engine **guides and verifies via `ProjectV2Workflow.enabled` but never enables**); the item-existence precondition (the sync tool **defensively, idempotently `item-add`s only items that already carry the engine label**, applying no label — the [control-plane](../spec/systems/infrastructure/control-plane.md) owns it, consumers read-only — so the engine populates the board with its own work whether or not auto-add is on, making auto-add a fuller-board convenience not a hard dependency); the fixed setup ordering (`project`-scope → `gh project create` → `gh project link` → operator-guided auto-add walkthrough + read-back), with the **UI walkthrough copy and read-back fail-message authored as owned content of the setup operation under the operator-communication law** (not a deferrable leaf); install-time disclosure of the manual auto-add step and of the engine placing its own items on the board; and the uninstall residuals extended to name the engine-added board items. **The material design change** came from the four-lens cold-session design audit (adversarial · technical-feasibility · non-engineer-operator · architect), which returned **2 blocking + several serious — all resolved before the lock by designed-doc edits, no locked-doc touch, no litigation alarm**: the first remediation draft homed the staleness marker in a **board-README fenced block** and called it "the same engine-namespaced-identity keying the module-system uses for shared files" — a **misappropriation of a locked term defined only over committed files** (blocking; adversarial + architect) that also wrote operator-shared external metadata, breaking the doc's own read-only-outward/uninstall story (blocking; adversarial) with a last-writer-wins clobber race (serious; architect). **Resolved by dropping the board-README write entirely and re-homing the staleness marker to a "last synced" engine-owned custom field on the engine's own item cards** — board-face where a non-engineer looks, purely the engine's own field (no clobber, no race, literally within "writes only its own custom fields") — which **dissolved both blocking findings and the operator's staleness-visibility serious at once**. The non-engineer-operator lens's other serious findings were remediated in-doc (install-time disclosure of the manual step; plain-language "thinner board"; committing the UI walkthrough + fail-message as owned operation content). The **technical-feasibility lens returned PLATFORM-FACTS-SOUND** on all seven claims (incl. the `addProjectV2ItemById` idempotency grounding the defensive add). **Both module-lock gates met:** the **build-readiness precondition** — a fresh dry-run over the remediated doc returned **BUILD-READY** (builder + spec-completeness reviewer; the one builder [serious], that the step-4 operator copy was "committed, not a leaf" yet ambiguously owned, fixed in-line by naming the setup operation as owner) — and the four-lens audit, followed by a **focused two-lens re-audit** of the revised doc: **adversarial LOCK-READY** (both blockers cured, the locked term gone, `item-add` correctly reads-only the label, no regression) and the operator lens's one residual serious — the doc-internal token "layer 2 above" leaking into the description of operator-facing copy ([§12](../principles.md)) — **fixed in-line** (a one-phrase strip). **Propagation (floor + ledger annotation + Q34 deletion):** the module doc (the remediated passages + `status: locked` via `lock.py`) + the locks.yaml entry (ratified_by D-149) + the frozen dry-run-ledger "Re-run after Q34 — BUILD-READY (D-149)" annotation (the [status-pointers/run-records](#) discipline — annotated, not rewritten) + [Q34](#) deleted from [open-questions.md](../reference/open-questions.md) + this entry. **No edit owed** to [modules/README.md](../reference/module-catalog.md) (design-maturity not catalog-tracked [D-090](0090-flesh-the-validators-core-module-doc-to-designed-the-engine.md); the `optional | core` row + `core →` edge unchanged), [engine-architecture.md](../architecture.md) (it does not name this module individually; the catalog carries it), [glossary.md](../reference/glossary.md) (no new/renamed term — the README-block term that would have needed one was removed), [risks.md](../reference/risks.md) (the engine-added-items residual sits within [R5](../reference/risks.md)'s accepted residual class), wbs/ (no dependency-graph change), or any locked doc. **No locked-doc edit, no litigation alarm** — the module consumes and relays the locked state/attention/telemetry/hooks/module-system/control-plane/provisioning laws and changes none. `python3 lock.py modules/github-projects-sync/README.md --decision D-149`; `python3 validate.py` green.

## Why

github-projects-sync was the higher-platform-risk of the two remaining v1 module locks because its value rests entirely on GitHub Projects v2 mechanics — and the [validate-against-the-live-system](#) discipline earned its keep twice: the technical-feasibility lens confirmed the Q34 platform-fact errors and the corrected facts, and the adversarial + architect lenses caught that the *first remediation draft itself* over-reached by writing the board README under a borrowed locked term. The right resolution ran *toward relaying less* (drop the external-README write, use the engine's own custom field) rather than editing the locked module-system — and that single move cured the locked-term misuse, the read-only-outward breakage, the clobber race, and the operator's staleness-visibility gap together. Every fix adapted the `designed` module to existing locked law, so all landed in-line; the lock proceeded on a clean dry-run, the audit-prescribed fixes, the focused re-audit's LOCK-READY, and green validation, atop the now-locked `core` and the locked state/attention/telemetry/hooks/module-system/control-plane/provisioning grammar — no churning neighbor.

## What we ruled out

**Keep "the engine enables the native auto-add automation"** (rejected — platform-impossible: no API/`gh` enables a built-in workflow; the engine can only guide and read `ProjectV2Workflow.enabled` to verify). **Home the staleness marker in a pinned card** (rejected — no pin API in Projects v2). **Home the staleness marker in a board-README fenced block** (rejected — it writes operator-shared external metadata with a last-writer-wins clobber race, breaks the read-only-outward/one-way framing, and the draft mislabeled it "engine-namespaced-identity keying," a locked term defined only over committed files; the engine-owned custom field on the engine's own cards is board-face, clobber-free, and literally within "writes only its own fields"). **Hard-depend the projection on auto-add being enabled** (rejected — auto-add is off by default and operator-UI-gated; the defensive idempotent `item-add` of already-labeled items populates the board with engine work regardless). **Defer the step-4 UI walkthrough copy + read-back fail-message as a build-spec leaf** (rejected — this is the one step the engine hands a non-engineer; a thin guide strands them, so the copy is owned content of the setup operation under the operator-communication law). **Lock on the first cold audit without remediation** (rejected — two blocking findings; locking through them would freeze a platform-impossible claim and a locked-term misuse). **Edit the locked module-system to extend engine-namespaced-identity keying to an external board README** (rejected — the litigation-class direction; the safe resolution removes the external write instead). **Edit catalog/architecture/glossary/risks to mark the lock** (rejected — floor only; design-maturity is not catalog-tracked).
