Ran the dry-run build simulation over the **L2 [product-design](../spec/modules/product-design.md)** module build step (module 2 of the remaining nine, module-by-module). The reviewer was **well-calibrated** (REJECTED F3/F4/F5 with verbatim cites; CONFIRMED only the two blockers — not the over-tagging profile [D-123](0123-run-the-l2-dry-run-validators-core-memory-substrate-both-bui.md) warns of). **Verdict: NOT BUILD-READY** — one confirmed BLOCKING finding, ground-truthed against the locked sources: **the engine-label scheme — the marker that makes a GitHub Issue engine-owned, and the sub-marker that makes one a product-design *spec* Issue (which [build-orchestration](../spec/systems/lifecycle/build-orchestration.md):151–152 must detect) — is consumed by ~8 living docs (telemetry, audits, state, attention, memory, build-orchestration, github-projects-sync, product-design) and OWNED by none.** [D-039](0039-reports-self-improvement-scope-engine-only-self-monitoring-o.md) (decision-log:276) established the engine-vs-product domain-label *concept* (history, not a living owner); [ontology](../spec/systems/grammar/ontology.md):121 assigns GitHub issue infrastructure to [control-plane](../spec/systems/infrastructure/control-plane.md)/topology and [telemetry](../spec/systems/guardrails/telemetry.md):83 routes debt to "a control-plane issue scaffold," so control-plane is the natural owner — yet control-plane has **zero** "label" references, names only three issue templates (bug/feature/engine-fault, control-plane:164), and never names the label scheme even as a build-spec leaf. The **FORM** the "engine-labeled Issue" leaf presupposes is itself unpinned (the genesis [Q27](#) meta-pattern, in a module the genesis run never reached). A secondary **serious** sub-finding: the in-Issue acceptance-criteria *content* shape is unpinned (prose-resolvable, but its owner should pin it). **The remedy re-litigates the LOCKED [control-plane](../spec/systems/infrastructure/control-plane.md)** (name/own the engine-label scheme + the spec-Issue marker as a build-spec leaf — directly analogous to [D-122](0122-enumerate-the-branch-ruleset-protection-floor-in-control-pla.md)'s protection-floor enumeration), possibly also touching the LOCKED [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) for the spec-detection contract. Per the litigation-alarm protocol (CLAUDE.md) and dry-run.md §6, I **STOPPED, ground-truthed against the locked source text, and raised the alarm to the operator — no doc was edited**. The run is appended to the dry-run ledger. `python3 validate.py` green.

## Why

The dry-run did exactly its job — it surfaced an underspecification invisible to a reader (every consumer cites "engine-labeled Issues" as if defined) but fatal to a builder (no living doc states the scheme). The signal is trustworthy, not a phantom: the builder and the well-calibrated reviewer independently CONFIRMED it (the reviewer rejecting 3 of 5 — not the over-tagging smell), and the orchestrator ground-truthed it against control-plane (zero label refs), telemetry (a consumer that defers to control-plane), build-orchestration (presupposes spec-detection, pins no marker), and ontology:121 (assigns the domain to control-plane). The gap is the same shape as [D-122](0122-enumerate-the-branch-ruleset-protection-floor-in-control-pla.md) finding #1 (a locked doc's role implies a contract its text never wrote) — handled there as a justified re-litigation, the precedent here. It is **upstream and cross-cutting**: product-design is merely the first module in the sweep that must EMIT a labeled spec Issue, so it hits the gap first; one control-plane fix unblocks every label-consuming module. Surfacing it now — rather than burying it under a pile of end-of-sweep findings — honors finding-disposition and lets the operator gate the locked-doc change before more agents run.

## What we ruled out

Treat the engine-label scheme as a **build-ready build-spec leaf** deferred to control-plane (rejected — §2 requires the FORM/owner be pinned, not just the value; control-plane's text neither defines the scheme nor names it as a leaf, only implies ownership via ontology:121 — the form is genuinely unpinned, the D-122 shape). Record product-design **BUILD-READY** anyway (rejected — its defining deliverable, the labeled spec Issue, cannot be built without inventing the scheme). **Edit control-plane now** to add the label scheme (rejected — it is LOCKED; the dry-run finds the case for change, it does not make it; the litigation-alarm protocol requires explicit operator approval first). **Lock product-design** (rejected — not build-ready; a blocking finding stands). **Continue the sweep silently** to module 3 (rejected — the gap is cross-cutting and litigation-class; the operator must weigh the locked-doc change before more label-consuming modules re-surface it). **Over-call the acceptance-criteria CONTENT shape as a second independent blocker** (rejected — it is prose-resolvable; recorded as a serious sub-finding folding into the same remedy, not inflated into a phantom).
