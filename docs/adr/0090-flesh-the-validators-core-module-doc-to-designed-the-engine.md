# Flesh the `validators-core` module doc to `designed`: the engine-self-validation rule corpus, consolidated, data-files-only

*Decided 2026-05-27 in the design workspace.*

## The decision

Take the [`validators-core`](../spec/modules/validators-core.md) module doc from `stub` → `designed` (packaging-view depth, matching the `designed` peers; **not** locked). `validators-core` ships the engine's **base self-validation rule corpus** — the concrete [check](../spec/systems/surfaces/check.md) data files that exercise [`core`](../spec/modules/core.md)'s validation engine against the engine's own surfaces: schema-conformance (`kind: schema`), the governed-shape + anti-changelog editorial lints (`kind: shape`), link integrity and catalog coverage (`kind: coverage`), PR-body completeness and the contract-anti-choice / close-disposition presence checks (`kind: presence`), and the knowledge fingerprint-coverage CI backstop (`kind: coverage`). The validation *laws* live in the locked [validation](../spec/systems/guardrails/validation.md) doc; the *engine* (thin dispatcher + the five closed kinds + suite declarations + triggers) is `core`'s ([D-089](0089-flesh-the-core-module-doc-to-designed-the-kernel-partition-t.md)); this module is the *content*. Three settled points: **(1) the mechanism/content split** — `core` ships the engine and **zero rules**, `validators-core` ships the corpus; safe because `validators-core` is `required`/always-present (no bootstrap rules needed in `core`; provisioning's first-run `coherence` is a direct kind-callable invocation). **(2) Consolidation** — the whole engine-self-validation corpus lives in this one package rather than scattered to each surface-owner; the locked [check](../spec/systems/surfaces/check.md) doc *permits* a non-owner module to ship a surface's checks, and self-validation is a coherent capability this module owns, so **feature** modules ship their own *domain* checks on top while this is the shared mechanical floor the dependents assume. **(3) Data-files-only (§16)** — `validators-core` ships check **data files only, zero kinds and zero detection**; the five kinds are `core`'s and each rule **relays** to an owner-held mechanism (the fingerprint-coverage rule invokes `core`'s `coverage` kind against [knowledge](../spec/systems/cognitive/knowledge.md)'s own fingerprint derivation; PR-body/presence rules relay the control-plane/contracts/close artifacts). `module-coherence` is not a rule here at all — it is the `coherence` kind invoked directly by provisioning's module manager over the installed-set manifests. **`wires: none`** (rules active by presence, §14; suite rosters derived); `depends: core`; `migrations: none (v1)`. The three inbound `depends` edges (`audit-library`, `dependency-discipline`, `engine-knowledge-graph`) are **mechanical presence assertions**, orthogonal to wiring.

## Why

A module doc is the packaging view; the corpus boundary is grounded in the locked [validation](../spec/systems/guardrails/validation.md) + [check](../spec/systems/surfaces/check.md) systems (*rules are data the validator consumes; the validator carries no rule of its own; suite membership is derived from the check files a module provides*) and in `core`'s [D-089](0089-flesh-the-core-module-doc-to-designed-the-kernel-partition-t.md) engine/corpus split, so `validators-core`'s doc maps that machinery → the rule-corpus bundle without restating laws. The closest `designed` peer is [audit-library](../spec/modules/audit-library.md) (a `required`, wires-nothing, active-by-presence module), and the doc mirrors its skeleton. A **cold plan-approach audit** (adversarial + architect lenses, with the plan **inlined** so the lenses could actually read it — the reachability fix after the [D-089](0089-flesh-the-core-module-doc-to-designed-the-kernel-partition-t.md) plan-stage audit ran blind on an out-of-sandbox plan path) ran before approval. Its valid findings are folded: the **§16 seam** — `validators-core` ships data files only, kinds/detection stay with owners, fingerprint-coverage relays knowledge (folded into the scope + the data-files-only section); the **mechanical-vs-semantic dependency** clarification (`depends` is presence, orthogonal to `wires`, so `wires: none` stands). Its raised-as-blocking *"each module ships its own checks, so why consolidate?"* was **downgraded** — the locked check doc permits a non-owner module to ship a surface's checks, so consolidation is not a contradiction — but the consolidation is now logged as an explicit decision with its anti-choice. Rejected-with-rationale: the *bootstrap-coherence gap* (first-run coherence is the direct `coherence` kind call over manifests, not a suite rule; `validators-core` is always present); *catalog-freshness / when coverage re-derives* (a runtime concern of the locked validation/knowledge foundations, not a packaging matter — build-spec leaf); *surface `validators-core` in [engine-architecture.md](../architecture.md) §6* (the master indexes systems, not modules — same rationale as [D-089](0089-flesh-the-core-module-doc-to-designed-the-kernel-partition-t.md)). A **second audit on the finished doc + this entry** (adversarial / architect / technical-feasibility, in-tree and fully reachable) then ran: the technical lens confirmed the kind-assignments against the locked validation/check docs; the agreed valid catch — the doc conflated a §16 *detection relay* (fingerprint-coverage relaying knowledge's mechanism) with *plain checks against externally-defined artifacts* (PR-body/presence, where `validators-core` owns the rule and the owner owns only the contract definition) — was folded by rewriting the data-only section to keep the two distinct, and the fingerprint `kind: coverage` was grounded in the locked knowledge doc's "fingerprint coverage check" naming with exact params marked a build-spec leaf. Rejected-with-rationale: *"this module is the content" is design-justification not current-state* (rejected — it mirrors the locked peer [audit-library](../spec/modules/audit-library.md)'s accepted "the laws live there; this module is how they ship" phrasing, not change-history cruft); *cross-cite the module-coherence exception into `core`'s doc* (rejected — `core` already locates the `coherence` *kind* in its engine and `validators-core`'s statement is self-sufficient; editing `core` for a cross-reference is unwarranted). Propagation per the matrix: [modules/validators-core/README.md](../spec/modules/validators-core.md) authored to `designed`; this entry. Verified no-change with rationale: [modules/README.md](../reference/module-catalog.md) (catalog row `validators-core | required | core` + the inbound graph edges already present; design-maturity is not catalog-tracked), [modules/core/README.md](../spec/modules/core.md) (`core` already names `validators-core` as the rule-corpus sibling at [D-089](0089-flesh-the-core-module-doc-to-designed-the-kernel-partition-t.md); this pass fills the sibling's own doc consistently — no edit to `core`), wbs/README.md (unauthored; gates the lock not the `designed` state), [glossary.md](../reference/glossary.md) (`Check-kind`, `Closed seam vocabulary`, `Required package` already defined; no new term), [engine-architecture.md](../architecture.md) (indexes via the catalog; the validation foundation's role unchanged). No locked system doc edited.

## What we ruled out

Ship base checks in `core` (rejected — splits the corpus, and `validators-core` is always-present so `core` needs no bootstrap rules). **Distribute each engine-self-check to its surface-owner** (rejected — fragments the single mechanical floor the three dependents assume as one base, and blurs the clean mechanism/content line). Ship check-*kinds* or detection mechanisms here (rejected — the five kinds are `core`'s closed set and detection stays with each owner per [§16](../principles.md); `validators-core` ships data files that relay). Author new kinds on spec (rejected — v1 rules use the five closed kinds; a kind extends by presence if ever genuinely needed, not pre-authored). Give it `wires` (rejected — checks are presence-active and rosters derived, and `depends` ≠ wiring). Lock `validators-core` this pass (rejected — its own dependents are still stubs; locking atop churning neighbors is forbidden, and the WBS + a fresh cold audit gate the lock, in dependency order after `core`).
