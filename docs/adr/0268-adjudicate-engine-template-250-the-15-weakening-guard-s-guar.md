# Adjudicate engine-template #250: the §15 weakening guard's guarded set is defined by an enforcement-gate **property** (fail-safe, derived), not the blanket `.engine/tools/` prefix; correct the live roster (drop non-gate tooling, add `.claude/settings.json`); no locked re-litigation

*Decided 2026-06-27 in the design workspace.*

## The decision

engine-template **#250** (engine-opened) reported that the [§15](../principles.md)/[D-051](0051-guardrail-integrity-the-builder-cannot-silently-weaken-its-o.md) guardrail-weakening guard (`engine-guard` → `.engine/tools/weakening_guard.py`) **over-fires** the deliberate `guardrail-ack`: its guarded roster includes the **blanket prefix `.engine/tools/`**, so any modification to a non-gate tool (session boot, memory, telemetry, the self-review renderer) demands the same deliberate acknowledgment as genuinely disabling a check — **training the rubber-stamping [D-051](0051-guardrail-integrity-the-builder-cannot-silently-weaken-its-o.md) explicitly closed** (its finding (2): "firing on benign installs trains rubber-stamping … alarm fatigue destroys the signal exactly when a weakening change must stand out"). The issue routes the call here because "what counts as a guardrail file" is a **design** question the build follows and never edits. **Ruling: the guarded set is defined by a property, not a path-prefix list; the live roster is non-conformant in both directions and the build owes the correction. No locked doc moves** (the [D-243](0243-decline-engine-template-238-s-public-repo-saved-memory-opt-i.md)/[D-251](0251-reject-engine-template-255-s-explore-gate-memory-carve-out-t.md) reject/adjudicate-and-record shape — the only design artifacts are this entry + a non-locked [glossary](../reference/glossary.md) refinement; `python3 validate.py` green, no lock fingerprint moves). A **four-lens cold audit** (adversarial · technical-feasibility · non-engineer-operator · architect, no shared context) ran against the draft adjudication; it **unanimously confirmed the destination** (a build-spec-leaf correction, no locked re-litigation, no workspace litigation alarm) and **materially corrected the mechanism and framing** — its blocking/serious findings are folded below.

  **The property (the design home).** A **guarded file** is a committed file that *constitutes or configures an enforcement gate* — one whose change could **remove, disable, rename, or loosen** a check, a permission / enforcement hook, or a branch protection. This is [§15](../principles.md)'s **own** by-property class (§15 names the categories *illustratively* — the deny/permission config, the CI workflows and check definitions, `CODEOWNERS`, the ruleset-affecting files — and **never** names `.engine/tools/`); the concrete path roster has always been a **build-spec leaf** ([D-051](0051-guardrail-integrity-the-builder-cannot-silently-weaken-its-o.md) "a leaf, not built now"; [control-plane](../spec/systems/infrastructure/control-plane.md) "the form is concretized at build time"; [validation](../spec/systems/guardrails/validation.md) owns the guard's *check wiring*, not the roster). **The roster was never adjudicated path-by-path in the corpus** ([D-207](0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md) treats `.engine/uv.lock` as *already* guarded; it did not add it) — which is itself the cleanest proof that #250 is a leaf correction, not a re-litigation.

  **Realization is derived and fail-safe** (the [§14](../principles.md) discovery axis; the [D-219](0219-authorize-the-first-run-travel-safety-re-litigation-a-retire.md)/[D-257](0257-resolve-re-lock-validation-the-negative-fixture-meta-check-l.md) "closed property, not an open category a build session self-classifies out of" discipline). The guarded set is a **permanent floor** *plus* every check rule's enforcement script **discovered by presence** — each `.engine/check/*.json`'s `params.script` path — so the ~16 hard `custom/script` enforcement scripts (scattered across `.engine/tools/` **and** its `dependency_discipline/`, `product_design/`, `migration_discipline/`, `external_contribution/` subpackages, with no shared naming convention) and **any future rule's script** are guarded **by being present**, never by a hand-list that silently drops them. **The default for an uncertain file is *covered*** (fail-safe): the asymmetry here is the inverse of [§19](../principles.md)'s (a wrongly-*excluded* §19 member is a recoverable missed regeneration; a wrongly-excluded **guarded** file is a *silently weakenable gate* — unrecoverable trust loss), so the property must pair with a covered-when-uncertain default that §19's class does not need — **which is exactly why §19 is *not* cited here** (it is also self-contradictory: `uv.lock` is a §19 **non-member** yet a §15 guarded member). Non-gate tooling (boot, memory, telemetry, self-review) is excluded **because it is neither a check script nor floor**, not by an exclusion list. The set-defining constant lives **inside a guarded file** (the guard's own script is a check script, hence in-set), so the definition stays self-protecting — [§15](../principles.md) non-falsifiability holds.

  **The live roster is non-conformant in both directions** (a **build-conformance / §15-fidelity** correctness finding — *not* a [§20](../principles.md) under-build, which targets milestone-*parked* capability; this guard is built and fires, it is built to too coarse a grain): **(over)** the blanket `.engine/tools/` prefix captures non-gate tooling — the over-firing #250 reports; **(under)** **`.claude/settings.json` is absent** from the guard though §15 mandates it — and the file *exists* on `origin/main`, enforcement-bearing (it wires the `PreToolUse` mode/permission gate `modes.py` and the other enforcement hooks). A PR that guts those hooks passes the guard with **no ack today** — a **live hole in the exact protection §15 exists to provide**, and on the merits the higher-severity half of #250. (§15's prose says "deny/permission blocks in `.claude/settings.json`"; the file enforces via **hooks**, not a `permissions.deny` array — the guarded-by-property reason is the hook enforcement, and §15's illustrative phrasing is not falsified by naming the realization precisely.)

  **The discriminator is already conformant and unchanged.** A pure addition strengthens; **remove / disable / rename / loosen / copy** can weaken (§15's own verbs; the guard's `WEAKENING_STATUS` already implements this, and correctly flags `copied` so a weakened *copy* of a gate cannot slip through). Narrowing fixes only the **non-gate population**; benign **modifications** to genuine gate files still carry the ack **by design** — the deliberate-review cost §15 intends ([D-207](0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md): a lockfile edit is "exactly where deliberate review belongs"). A **comment-only / whitespace-only carve-out is rejected**: it would make the guard **falsifiable by the change it judges** (a comment-aware parser is gameable — a semantic no-op the parser misreads becomes a silent bypass), the operator does not want a second thing to trust they cannot check, and once the *set* is narrowed the residual is edits to the few enforcement-code files — precisely where deliberate review belongs. Fail-closed stays the law ([D-257](0257-resolve-re-lock-validation-the-negative-fixture-meta-check-l.md)).

  **The narrowing PR is itself a §15 weakening (coverage-narrowing) and self-acks.** Removing the blanket prefix **reduces guard coverage**, which is a weakening-class change ([§15](../principles.md); the [risks.md R1](../reference/risks.md) check-coverage-narrowing clause, [D-207](0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md)). Because the set-defining constant is in a guarded file, the narrowing PR **trips the guard** and lands only behind the operator's `guardrail-ack`, **plain-language-relayed** ([control-plane](../spec/systems/infrastructure/control-plane.md) merge surfacing / [§12](../principles.md) leak guard) — naming which file class leaves the guarded set and what the AI could then edit unwatched. (The `.claude/settings.json` **addition** is *strengthening* — it passes clean, no ack — and is separable; land it first.) This is the issue's own anticipation ("whatever the fix, it is itself a guardrail change … carries its own one-time acknowledgment").

  **Build-owes (engine-template #250 lineage, to be filed citing this entry via [`issue_author.py`](https://github.com/StarshipSuperjam/engine-template) + the `engine` label — build under-/mis-conformance to existing locked §15, not a design gap):** **(i, highest — closes the live hole)** **add `.claude/settings.json` to the guarded set** (it exists and enforces via `PreToolUse` hooks; strengthening, no ack, non-deferrable); **(ii)** replace the blanket `.engine/tools/` prefix with the **derived fail-safe set** — the permanent floor (`validate.py`, `weakening_guard.py`, `.engine/check/` rule JSONs, `.github/workflows/`, `.github/CODEOWNERS`, `.engine/pyproject.toml` + `.engine/uv.lock`, `.engine/suites.json`, `.claude/settings.json`) **plus every `.engine/check/*.json` `params.script` path**, including the **provisioning ruleset-applying operation** (a §15 "ruleset-affecting file" — the ruleset itself does not travel as a file, so its applying code is the guarded proxy); **(iii)** **before dropping anything, audit what currently matches `.engine/tools/` against the property** so a genuine gate that happened to live under the prefix is not silently dropped; **(iv)** the narrowing PR **self-acks** with the plain-language coverage-loss relay (above); **(v)** a **regression test** pinning `validate.py` + `weakening_guard.py` as permanent in-set members (the self-protection property must not silently lapse).

  **Verify-no-edit dispositions (recorded, not skipped — the [D-251](0251-reject-engine-template-255-s-explore-gate-memory-carve-out-t.md) discipline):** [principles §15](../principles.md) (states the class by category, never the leaf — and the audit-required grep confirms the locked [control-plane](../spec/systems/infrastructure/control-plane.md) text contains **no** `.engine/tools/` over-claim sentence to neutralize, the [D-207](0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md)/[D-208](0208-resolve-the-d-207-dependabot-pr-contract-exemption-landed-te.md) check); [control-plane](../spec/systems/infrastructure/control-plane.md) (owns the §15 contract; delegates the roster — no edit), [validation](../spec/systems/guardrails/validation.md) (owns the guard's *check wiring*, not the roster — no edit), [check](../spec/systems/surfaces/check.md) / [modules/core](../spec/modules/core.md) / [modules/validators-core](../spec/modules/validators-core.md) (grammar + instance, roster-silent — no edit), scenarios + [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) plan-gate + control-plane PR contract (the surfacing seam is unchanged — no edit), [engine-architecture](../architecture.md) (role+link index — no edit), [risks.md R1](../reference/risks.md) (the residual is the **existing** §15 weakening / check-coverage-narrowing class [D-207](0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md) already folded — no new R, no edit). **Non-locked propagation (this pass):** [glossary](../reference/glossary.md) *Guardrail integrity* refined to **property altitude** (the enforcement-gate property + the non-gate-tooling exclusion + the fail-safe derived realization; **no path list** — a roster in the glossary would rot and mis-home the leaf); its siblings *Weakening acknowledgment* + *Protection floor* verified consistent (neither implies "any tools edit fires") — no edit owed.

## Why

#250's symptom (over-firing) and its honest defense (a `pull_request_target` guard reads the diff and never runs head code, so it "can't tell a strengthening tool-edit from a weakening one by looking") both point at the same root: the **set**, not the discriminator. The discriminator (additions strengthen; remove/disable/rename/loosen/copy weakens) is already §15-conformant; the rubber-stamping comes from the blanket prefix sweeping in non-gate tooling, and the cure is to scope the set to the enforcement-gate **property** §15 already defines. The four-lens cold audit earned its keep and **reshaped the fix away from the obvious-but-wrong patch**: the plan's first draft proposed *naming the enforcement-logic subset explicitly* — the technical-feasibility lens proved that is **fail-open** (the ~16 hard enforcement scripts scatter across four subpackages with no naming convention, and the closed check-kinds are functions *inside* `validate.py`), so a hand-list silently un-guards real gates, the exact over-correction of the over-firing; the adversarial + architect lenses independently demanded a **closed property with a fail-safe default** ([D-219](0219-authorize-the-first-run-travel-safety-re-litigation-a-retire.md)/[D-257](0257-resolve-re-lock-validation-the-negative-fixture-meta-check-l.md)) and caught that the draft's **§19 citation was a misapplication** that actively contradicts the set (`uv.lock`), and that the **narrowing PR must itself carry the ack** ([D-207](0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md)/R1); the technical lens ground-truthed that **`.claude/settings.json` is present and hook-enforced** (the build-owe says "add to the guarded set," not "create it"); the operator lens confirmed the fix **restores** the rare-and-meaningful acknowledgment and asked that the in/out classes reach the operator in plain prose at the one disclosure (folded into the self-acking narrowing relay). Recording the property + the build-owe in the log rather than touching locked §15 is the proportionate, lock-discipline-faithful home: the roster is a leaf the locked docs already delegate, and a re-lock + cold audit of §15 for a leaf correction the log can carry is the unjustified churn the discipline guards against ([D-251](0251-reject-engine-template-255-s-explore-gate-memory-carve-out-t.md)/[§11](../principles.md) shape).

## What we ruled out

**Re-litigate locked [§15](../principles.md) into an explicit property/roster form** (rejected — §15's category list is illustrative and not false; the roster was never path-by-path adjudicated and is a build-spec leaf control-plane/validation already delegate; re-locking a principle for a leaf correction is the just-locked-doc churn lock discipline forbids — the fix fits *below* the lock). **Name the enforcement-logic subset of `.engine/tools/` as a hand-list** (rejected — **fail-open**: it silently un-guards the ~16 scattered hard enforcement scripts and every future rule's script, the precise over-correction of the over-firing; the derived-by-presence fail-safe set is the only realization that cannot under-include). **Cite [§19](../principles.md) as the membership-by-property precedent** (rejected — §19's property is source-determinism with a *recoverable* exclusion risk; the guarded set's exclusion risk is *unrecoverable*, so it needs a fail-safe default §19 lacks, and §19's own roster excludes `uv.lock`, a §15 member — the citation would be self-contradictory; cite §15's own class + [D-207](0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md) + [D-219](0219-authorize-the-first-run-travel-safety-re-litigation-a-retire.md)/[D-257](0257-resolve-re-lock-validation-the-negative-fixture-meta-check-l.md)). **Add a comment-only / whitespace-only non-weakening carve-out** (rejected — it makes the guard falsifiable by the change it judges, [§15](../principles.md); the operator declines a second unverifiable trust surface; fail-closed is the law [D-257](0257-resolve-re-lock-validation-the-negative-fixture-meta-check-l.md)). **Land the narrowing PR on an ordinary one-click merge** (rejected — coverage-narrowing is itself a §15 weakening, [D-207](0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md)/R1; the narrowing PR self-acks with the plain-language coverage-loss relay). **Frame #250 as a [§20](../principles.md) under-build** (rejected — §20 targets capability *parked behind a milestone*; this guard is fully built and fires, merely to too coarse a grain — ordinary build-conformance correctness, and over-loading the freshly-minted §20 cuts against [D-266](0266-new-principle-20-spec-conformance-is-the-standing-target-no.md)'s deliberately narrow scope). **Treat #250 as a pure build bug, skip the log ruling** (rejected — it adjudicates the scope of a *locked* trust contract; the ruling is recorded history per the litigation protocol, and the build-owes alone would lose the *why*). **Open a new risk / glossary term / principle** (rejected — the residual is R1's existing §15 class, the term *Guardrail integrity* already exists, and the binding *applies* §15/§14; [R6](../reference/risks.md)/[D-255](0255-sharpen-the-post-v1-revisit-triggers-for-product-knowledge-g.md) anti-sprawl).
