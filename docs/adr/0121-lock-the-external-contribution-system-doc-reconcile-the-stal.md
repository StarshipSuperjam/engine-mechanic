# Lock the `external-contribution` system doc; reconcile the stale pending-seam wording; defer the module-packaging lock to its dry-run build

*Decided 2026-05-29 in the design workspace.*

## The decision

Ratify and **lock** [external-contribution](../spec/systems/lifecycle/external-contribution.md) (`status: designed → locked`) — the cross-repo contribution mode's **laws** ([D-102](0102-cross-repo-external-contribution-as-a-first-class-v1-operati.md)/[D-103](0103-cross-repo-design-cold-audit-resolutions-engine-clean-branch.md)/[D-106](0106-elaborate-the-external-contribution-doc-with-the-cross-repo.md)). The lock's three gates are met: the WBS sort is authored ([D-107](0107-author-the-wbs-module-build-order-the-builder-crossover-reso.md)), the dependency [core](../spec/modules/core.md) is locked ([D-120](0120-lock-core-the-root-module-the-closure-wave-s-terminal-ratifi.md)), and **all four Phase-C locked-doc seams already landed at [D-104](0104-phase-c-cross-reference-the-external-contribution-mode-into.md)** — the three additive cross-references (provisioning/control-plane/topology) **and the substantive build-orchestration close-model change** (the merge wall moves from the operator's merge to the upstream's, [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) §Close). So **no build-orchestration re-litigation remains** — this entry **supersedes [D-120](0120-lock-core-the-root-module-the-closure-wave-s-terminal-ratifi.md)'s loose "the pending D-104 external-contribution close re-litigation" phrasing**, which was stale at authoring (D-104 had landed and re-locked that clause the prior day). What this pass actually does is remediate a **propagation miss**: D-104/D-107/D-120 left forward-looking "pending / deferred / gated" language in several `designed` docs, an authoring-rule-1 violation that also blocks a truthful lock (a body cannot lock while misstating its own state). Reconciled to current truth: the system doc's §"Upstream has two senses" / §"Packaging" / §"Design commitments" (seams **landed**, not deferred), [engine-architecture.md](../architecture.md) §3, [modules/README.md](../reference/module-catalog.md), and [risks.md](../reference/risks.md) R13. Two honesty additions realize the already-decided [R14](../reference/risks.md) mitigation in the docs: a system-doc §"Design commitments" bullet committing that **the install discloses the cross-repo path is un-exercised end-to-end at v1** (the [clean-code](../spec/modules/clean-code.md) disclosure precedent), and the matching line in the [module](../spec/modules/external-contribution.md) §"Setup-time disclosure". **Scope is operator-directed: the SYSTEM (laws) doc locks now; the MODULE (packaging) doc stays `designed`** and locks later, after a **clean dry-run build over its build step** — the build-readiness precondition for a module-packaging lock, distinct from the cold-session audit that gates a system-laws lock (the [D-110](0110-run-the-genesis-dry-run-through-complete-core-log-the-build.md)→[D-120](0120-lock-core-the-root-module-the-closure-wave-s-terminal-ratifi.md) `core` precedent). That gate role is recorded in wbs/dry-run.md §1. [R13](../reference/risks.md) (platform-fact validation) and [R14](../reference/risks.md) (un-exercised at v1) **stay open** — build-time concerns the design names honestly with verification gates.

## Why

`external-contribution` is lockable now because every law it rests on is `locked` (check, build-orchestration, control-plane, topology, provisioning, state, knowledge, memory, attention, telemetry, operations, docs, policies) and its only `designed`/`stub` references (the module itself, [product-knowledge-graph](../spec/modules/product-knowledge-graph.md), [clean-code](../spec/modules/clean-code.md)) are neighbour-leaf / future-remedy references the lock discipline permits, not law dependencies — so no neighbour's later settling can force a re-lock. The system/module split is the honest division the lock vocabularies already imply: **system docs lock on the cold-session audit (soundness); module-packaging docs lock on the dry-run build (buildability)** — the operator's rule this session, matching how the genesis dry-run ([D-110](0110-run-the-genesis-dry-run-through-complete-core-log-the-build.md)) gated `core`'s lock ([D-120](0120-lock-core-the-root-module-the-closure-wave-s-terminal-ratifi.md)). The **HARD cold-session design audit** (the CLAUDE.md gate) ran four independent cold-context lenses (adversarial · technical-feasibility · non-engineer-operator · architect) against the finalized doc: **no blocking or serious finding**. The technical lens re-verified the keystone platform fact against current GitHub + the live engines — a fork→upstream pull request runs the **upstream's** own required checks in the upstream's context regardless of fork settings (first-time-contributor approval only strengthens the wall), the cross-fork `gh pr create --repo <upstream> --head <owner>:<branch>` works for an operator-owned fork, a fork's CODEOWNERS has no cross-repo teeth, and R13's three deferred facts are honestly gated, not silently assumed. Nits logged, none blocking: an **org-owned** fork-head is outside the v1 envelope (the design scopes to an operator-**owned** fork; a build-spec note); **"DCO/CLA"** stays maintainer-layer naming and the build-spec narration copy keeps the acronym out of operator-shown text ([§12](../principles.md) leak guard); the clean-code disclosure precedent is a benign forward-reference (the pattern is already established at [D-095](0095-cut-expression-contracts-disposition-prose-organization-cove.md)). `python3 lock.py systems/lifecycle/external-contribution/README.md --decision D-121`; `python3 validate.py` green. **Propagation:** the system doc locked + the locks.yaml entry (ratified_by D-121); the reconciled docs (system, [module](../spec/modules/external-contribution.md), [engine-architecture.md](../architecture.md) §3, [modules/README.md](../reference/module-catalog.md), [risks.md](../reference/risks.md) R13) + the dry-run §1 gate-role note; this entry. **No edit owed** to [glossary.md](../reference/glossary.md) (the four terms — external contribution, fork-native, engine-mechanic, upstream two senses — are current, and a lock changes no term meaning) or [scenarios/external-contribution.md](../architecture.md#contributing-to-an-external-repo) (reads current-state), both confirmed by the architect lens; no CLAUDE.md document-map edit (no top-level doc/group added).
