# Memory & validators-core are hand-governed Builder-A builds; memory gets a light build-order map (not a single session, not orchestration-dogfooded)

*Decided 2026-06-05 in the design workspace.*

## The decision

The two M1-completing modules — [validators-core](../spec/modules/validators-core.md) and [memory-substrate-sqlite-fts5](../spec/modules/memory-substrate-sqlite-fts5.md) — are built by **Builder A, hand-governed** under the stage-0 harness, **affirming the canon as written** (module-order §4/§5; [D-107](0107-author-the-wbs-module-build-order-the-builder-crossover-reso.md)), not reinterpreting it. Memory is **not a single session**: being ~6–7 units of trust-critical machinery (the non-regenerable NDJSON ledger + its integrity law, the derived FTS5 index + scan fallback, capture + the closed role-vocabulary, active-forgetting, the `search` implementation + MCP, and the backup/restore that closes [R2](../reference/risks.md)), it is decomposed by a new **light, hand-authored build-order map**, wbs/memory-build-plan.md — the lower-risk analog of core-build-roadmap.md: source-wins, carries no design detail, deleted when the memory build completes. [validators-core](../spec/modules/validators-core.md) is **data-files-only** ([D-090](0090-flesh-the-validators-core-module-doc-to-designed-the-engine.md)) and needs no separate map. build-orchestration's **first real self-build is post-M1** ([routine-mode](../spec/modules/routine-mode.md)/[audit-library](../spec/modules/audit-library.md)), run **with memory present**. Three obligations are pinned for the memory build, durable in module-order §5 + the map: a **ledger-before-hooks ordering invariant** (the build session wires memory's own `Stop`/`SessionStart` hooks, which fire on its own turns — registration follows the ledger; interim hooks are safe no-ops; write-safety is the ledger-integrity law, not hook ordering); the **R2 consent floors** (consent-before-create, the committed backup README, the privacy re-check) as named operator-visible gates; and the **end-to-end exercise of the two `core` seams that shipped inert** without a ledger/index — the [close](../spec/systems/lifecycle/close.md) ambient-capture relay and the [attention](../spec/systems/cognitive/attention.md) scent. **No locked doc is edited and no system is locked** by this entry.

## Why

The bootstrap is sound either way — build-orchestration provably operates with memory **absent**: [core](../spec/modules/core.md) declares `depends: —`; every memory touchpoint degrades-to-absent or is inert ([boot](../spec/systems/lifecycle/boot.md) orients from committed state "and says so, loudly"; [close](../spec/systems/lifecycle/close.md) "only triggers it and never gates it"; the scent fail-opens); and the `search` interface is a **core-shipped *protocol* whose FTS5 *implementation* is memory's own** ([modules/core](../spec/modules/core.md)), so during memory's own build recall is **absent, not slow**. Given that, the live choice is *which builder*, and hand-govern wins: **dogfooding memory buys no review depth** — at M1 the build-orchestration review lenses ([design-review](../spec/modules/design-review.md)/[qa-review](../spec/modules/qa-review.md)) are post-M1 optionals that no-op, and build-conformance + the behavioral demo is the cold-review spine for engine self-construction throughout v1 (module-order §5) — while it **would** debut never-run orchestration machinery *degraded* on the most trust-critical, non-regenerable substrate, and force a needless crossover-model revision (the canon defines Builder A as un-substrated/no-build-orchestration and Builder B as the engine using committed modules). Keeping the canon literal lets build-orchestration's first real self-build be a later, lighter module run with its full substrate present — a fairer first exercise. Surfaced and resolved through a four-lens cold audit (adversarial · technical-feasibility · non-engineer-operator · architect), which favored this path and supplied the three pinned obligations above.

## What we ruled out

**Dogfood memory via build-orchestration** (rejected — no review-depth gain over hand-govern, since the orchestration lenses no-op at M1; debuts unproven machinery degraded on the cornerstone; needs a crossover-model revision for zero safety benefit). **Single session** (rejected — far too light for ~6–7 trust-critical units incl. the ledger-integrity law and R2). **A heavy 27-slice-style ceremony for memory** (rejected — disproportionate; a light source-wins map suffices). **Pre-decompose memory inside module-order** (rejected — module-order is deliberately module-granularity; the slice-level decomposition lives in its own transient map, the core-build-roadmap precedent). **Home the inert-seam obligation only in core-build-roadmap.md** (rejected — that file is deleted at slice 27, before memory builds; the durable home is module-order §5 + the memory map). **Leave the builder under-specified** (rejected — the canon read two ways; the bootstrap question must be settled before the build reaches memory).
