# Flesh the `routine-mode` module doc to `designed`: the operator entry into the Routine stance, wiring nothing

*Decided 2026-05-27 in the design workspace.*

## The decision

Take the [`routine-mode`](../spec/modules/routine-mode.md) module doc from `stub` → `designed` (packaging-view depth, matching the `designed` peers; **not** locked). `routine-mode` ships the operator's **entry** into the unattended Routine stance: the **`/engine-routine`** [skill](../spec/systems/surfaces/skills.md) (`invocation: operator-typed`, engine-prefixed — the thin entry command a Local Desktop routine's Instructions fire, carrying no step list) + the **routine-entry [operation](../spec/systems/surfaces/operations.md)** it delegates to (confirm the unattended posture, read the frozen scope-locked build Issue, first-fire echo, misfire-as-Issue, then enter the build-orchestration routine workflow). `status: required`; `wires: none`; `depends: core`; `migrations: none (v1)`. The Routine *stance laws* live in locked [modes](../spec/systems/lifecycle/modes.md) and the unattended *workflow* in locked [build-orchestration](../spec/systems/lifecycle/build-orchestration.md); the module restates neither. Two boundary points are settled: **(1) `wires: none` holds** because nothing wire-like is `routine-mode`'s — the **non-interactive permission posture** is an **operator-side Claude Desktop "Default/Auto" preset** ([D-088](0088-justified-re-litigation-name-the-routine-entry-command-engin.md) build-spec cautions; the mode is not introspectable at runtime, the operator is the gate), configured *outside* the committed repo and so outside the closed `permission` seam entirely (the same basis as the OS-temp stance-signal marker); the **push wrapper + unattended Default-Branch-Push gate** are build-orchestration **build-spec leaves** ([D-088](0088-justified-re-litigation-name-the-routine-entry-command-engin.md)), authored in the build pass; the **Explore write-gate `PreToolUse` hook** is registered by modes and packaged by `core`. **(2)** the single-referrer **routine-entry operation is preserved on a ratified affirmative case** — it is *not* one skill's private depth but the [D-087](0087-resolve-q7-v1-skill-membership-close-deviation-d2-the-wbs-de.md)/[D-088](0088-justified-re-litigation-name-the-routine-entry-command-engin.md) cold-audited **drift-firewall** (the scope-read / first-fire echo / misfire-as-Issue logic kept in one authoritative home, not buried in a thin command or in build-orchestration prose), satisfying the locked [operations](../spec/systems/surfaces/operations.md) anti-sprawl bar rather than defaulting past it.

## Why

A module doc is the packaging view; the depth lives in the locked modes/build-orchestration/skills/operations systems plus the ratified [D-087](0087-resolve-q7-v1-skill-membership-close-deviation-d2-the-wbs-de.md)/[D-088](0088-justified-re-litigation-name-the-routine-entry-command-engin.md) entry, so the doc maps that machinery → the entry bundle without restating laws. The closest `designed` peer is [audit-library](../spec/modules/audit-library.md) (a `required`, wires-nothing, active-by-presence module); the doc mirrors its skeleton. The **session-level cold plan-audit** (adversarial + architect lenses, plan inlined) served as this module's plan-approach audit — it vetted `routine-mode`'s manifest/wires/boundary and raised exactly two items, both **discharged in grounding before authoring**: "verify the non-interactive/permission posture + push-wrapper ride core, not routine-mode" and "state the single-referrer operation's anti-sprawl affirmative case." A **cold finished-doc audit** (adversarial / architect / technical-feasibility, in-tree) then ran on the doc + this entry. The **architect lens passed clean** (carve-out fidelity exact against `core` line 70; the §16 ownership split verified verbatim against the locked sources; every no-edit propagation claim verified). The **adversarial and technical lenses caught real defects in the *justification* of `wires: none`** (the manifest value itself is correct): the draft claimed the permission posture and push-wrapper "ride `core`," but `core`'s only `permission` wire is read-access and those artifacts live in no system body — so the basis was reworded to the honest one (operator-side Desktop preset outside the seam; build-orchestration build-spec leaves), and a **dangling "modes §16" citation** (modes is not section-numbered; §16 is a `principles.md` principle) was repointed to the modes Routine ownership boundary + the [§16](../principles.md) axis, with the Explore write-gate hook re-attributed to core/modes. All folded into [modules/routine-mode/README.md](../spec/modules/routine-mode.md). Propagation per the matrix, verified no-change with rationale: [modules/README.md](../reference/module-catalog.md) (the `routine-mode | required | core` row + the `core → routine-mode` edge already present; design-maturity not catalog-tracked), [modules/core/README.md](../spec/modules/core.md) (line 70 carve-out "the routine stance + `/engine-routine` entry" accurate — the module ships only the entry, the stance is `required` core; no edit, per the [D-090](0090-flesh-the-validators-core-module-doc-to-designed-the-engine.md)/[D-091](0091-flesh-the-memory-substrate-sqlite-fts5-module-doc-to-designe.md) no-edit-core precedent after an affirmative accuracy check), [glossary.md](../reference/glossary.md) (`Mode (stance)`, `Skill`, `Command`, `Operation` already cover it; `/engine-routine` is a pinned instance name, not a new term — no edit, matching [D-088](0088-justified-re-litigation-name-the-routine-entry-command-engin.md)'s verified glossary no-change), [engine-architecture.md](../architecture.md) (§7/§9 index systems via the catalog; the routine-stance mention stays truthful), wbs/README.md (unauthored; gates the lock not the `designed` state). No locked system doc edited.

## What we ruled out

Give `routine-mode` a `permission` wire for the non-interactive posture (rejected — the posture is an operator-side Claude Desktop preset outside the committed repo, not a `.claude/settings.json` entry, so it is outside the seam; were it committed, `core`/build-orchestration would own it, never this module). Justify `wires: none` by saying the permission posture/push-wrapper "ride `core`" (rejected — checkably false: `core`'s only `permission` wire is read-access and the push-wrapper lives in no system body; the honest basis is operator-side-preset + build-orchestration build-spec leaves). Fold the routine-entry procedure into the `/engine-routine` skill's bundled depth (rejected — [D-087](0087-resolve-q7-v1-skill-membership-close-deviation-d2-the-wbs-de.md)/[D-088](0088-justified-re-litigation-name-the-routine-entry-command-engin.md) ratified an owned operation as the drift-firewall; collapsing it was the logged anti-choice there). Have `routine-mode` own the unattended workflow or the push-wrapper (rejected — modes assigns the workflow to build-orchestration; `routine-mode` owns only the stance entry). Restate the modes stance laws in the module doc (rejected — the laws live in the locked system; the module applies them). Lock `routine-mode` this pass (rejected — the WBS + a fresh cold audit gate the lock, in dependency order after `core`).
