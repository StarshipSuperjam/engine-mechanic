# Lock `migration-discipline` (product-migration governance): the sixth module lock

*Decided 2026-05-30 in the design workspace.*

## The decision

Ratify and **lock** [migration-discipline](../spec/modules/migration-discipline.md) (`status: designed → locked`) — the `optional` SCM module governing the **product's** data/schema migrations (a posture discipline policy + a `soft` ecosystem-detected presence check + read-only detection), the **sixth module lock** and the first of the SCM trio. **Both gates met:** build-readiness at the L2 dry-run (BUILD-READY, all four dry-run lenses; no contradictions across 7 axes), and the **HARD cold-session design audit** — four cold-context lenses **all ratify, no blocking and no serious finding**. The lenses confirmed: the **honest tiers** ([§7](../principles.md)) — the discipline bar is posture, the destructive-migration escalation is "posture-grade, not mechanical teeth" (migration safety is not mechanically decidable across ecosystems; there is no native migration-safety database to relay the way [dependency-discipline](../spec/modules/dependency-discipline.md) relays GitHub's vulnerability data), and the presence check is `soft` — nothing dressed as enforced; the **[§16](../principles.md) escalation relay** into the always-present locked [Escalation policy](../spec/systems/surfaces/policies.md) (which already escalates "irreversibility or external blast radius" with or without this module — verified) registers/edits nothing; **`depends: core` on the target axis** ([D-129](0129-reconcile-dependency-discipline-to-depends-core-l2-the-targe.md), this module's origin case — the check inspects PRODUCT artifacts and presupposes no engine-self-validation corpus, so it needs only `core`'s check engine, never [validators-core](../spec/modules/validators-core.md); no sibling-L2 edge); the **product/engine migration boundary** is terminological only (the engine's own `migrations` mechanism — provisioning upgrade migrations, the memory ledger unit, schema version-pinning — shares no code/file/seam with the product tooling this module governs); the **[§13](../principles.md) wall** holds (read-only inspection, never runs a product migration or edits product source; the removal test is *strengthened* — core still escalates irreversibility). The technical lens ground-truthed every platform mechanism (a `soft` check rides the single ruleset-bound CI job by self-declaration and never becomes a required-status gate; read-only PR-artifact inspection needs no migration execution; the interactive-stop / routine-halt-and-route escalation matches the headless "cannot ask" constraint; ecosystem detection by manifest *or* tooling config/convention is realizable; the no-native-safety-database contrast is accurate). The operator lens confirmed the destructive-migration escalation hands a non-engineer a real decision bundle (what it does · the data-loss risk · options · a recommendation · a concrete safer path) not a bare menu, stops-and-asks-never-vetoes, holds routine ≥ interactive, and discloses not-applicable/no-op honestly. **Nit dispositions (none blocking):** the parenthetical "the framework has no rollback concept (Prisma, free-tier Flyway/Liquibase)" is slightly overstated (Prisma supports down-migrations via `migrate diff`, just not auto-generated) — **left**, as the ecosystem names are explicitly "examples, not a closed set" and the ecosystem table + precise per-framework rollback semantics are a declared build-spec leaf to pin against then-current tool docs; the "explain, never dumb down" operator-term list could also name `backup-first`/`additive-then-cutover` — a **build-spec wording leaf** (the destructive-migration message is a first-class operator surface to draft and behaviorally exercise at build); the dense `provides`/`migrations` table cells — **left** (the [D-138](0138-lock-validators-core-the-base-self-validation-rule-corpus-th.md)–[D-141](0141-lock-product-design-the-design-front-door-the-fifth-module-l.md) manifest-table symmetry disposition; the `migrations` gloss earns its place disambiguating the terminological collision). **Propagation (floor only, architect-confirmed):** the module doc (`status: locked` via `lock.py`) + the locks.yaml entry (ratified_by D-142) + this entry. **No edit owed** to [modules/README.md](../reference/module-catalog.md) (design-maturity not catalog-tracked [D-090](0090-flesh-the-validators-core-module-doc-to-designed-the-engine.md); the SCM catalog row + `core → migration-discipline` edge unchanged), [engine-architecture.md](../architecture.md) (indexes systems; the roster mention is truthful and carries no lock-state), [glossary.md](../reference/glossary.md) (no term coined; migration-discipline already named), [risks.md](../reference/risks.md) (the [R5](../reference/risks.md) containment story is unchanged), wbs/ (L2 placement + frozen ledger unchanged; the ledger entry is clean BUILD-READY with no open finding, so no "Resolved by" annotation owed), or the CLAUDE.md document map. **No locked-doc edit, no litigation alarm** — the lock consumes the locked policies/check/validation/topology/core laws and changes none. `python3 lock.py modules/migration-discipline/README.md --decision D-142`; `python3 validate.py` green.

## Why

migration-discipline is the first SCM-trio lock and the cleanest optional yet — all four lenses ratified with no blocking/serious, the module's defining virtue being that it volunteers its own non-mechanical limits ("no mechanical destructiveness detector"; posture-grade, not teeth) rather than over-claiming, which is exactly what [§7](../principles.md) and the non-engineer-trust model demand. It is upstream-anchored on the locked `core`, standalone (fills no Slot), and its escalation relays into an always-present locked policy, so it sits atop no churn. The Prisma/free-tier nits are illustrative-example imprecision in a parenthetical whose precise table is a declared build-spec leaf — leaving them is consistent with deferring concrete values, not an MVP omission.

## What we ruled out

**Lock on the dry-run alone, skipping the cold audit** (rejected — every packaging lock owes its own four-lens cold audit + operator go, the [D-120](0120-lock-core-the-root-module-the-closure-wave-s-terminal-ratifi.md)–[D-141](0141-lock-product-design-the-design-front-door-the-fifth-module-l.md) precedent). **Tighten the Prisma "no rollback concept" example before lock** (rejected — it is an illustrative parenthetical, the doc frames the ecosystems as "examples, not a closed set," and the ecosystem table + per-framework rollback semantics are an explicit build-spec leaf to pin against then-current tool docs; folding a build-spec-leaf example detail would deviate from auto-proceed-on-clean for a non-load-bearing nit). **Add `backup-first`/`additive-then-cutover` to the explain-terms list now** (rejected — the destructive-migration operator message is a build-spec wording leaf drafted and behaviorally exercised at build; the *requirement* — explain domain terms, never dumb down — is already pinned). **Dress the escalation as mechanical teeth** (rejected — migration safety is not decidable across ecosystems; honest posture backed by the human gate is the truthful tier, [§7](../principles.md)). **Give it a `validators-core` edge** (rejected — [D-129](0129-reconcile-dependency-discipline-to-depends-core-l2-the-targe.md) target axis: it inspects product artifacts, needs only `core`'s check engine). **Edit catalog/architecture/glossary/risks to mark the lock** (rejected — no propagation owed beyond the floor, architect-confirmed).
