## Why

dependency-discipline carried the highest seam-subtlety of the sweep because its accepted-exception consent had to relay into the locked §15 weakening-acknowledgment without a locked-doc change, and the crux was whether the §15 guard's monitored scope already covers a module's allow-list. The audit confirmed it does: §15 names "check definitions" as a **category** (not a frozen path-list), the allow-list is a check rule's own committed `params`, and loosening it is the §15 verb *loosening a guardrail* — so the existing guard fires natively, a relay not a litigation. The operator chose the §15 weakening-acknowledgment over the lighter per-PR disposition because a durable, forward-looking reduction in security coverage warrants the deliberate gesture, not a one-click pass that a permanent coverage hole could ride. Every finding adapted the `designed` module to existing locked law (home the allow-list as a check definition; clarify first-party-not-third-party; make the §15 scope-match explicit), so all landed in-line; the lock proceeded on the platform-facts-sound + architect-clean + operator-safe verdicts, the build-ready dry-run, the resolved findings, the focused re-check's LOCK-READY, and green validation — atop the locked `core` / check / validation / control-plane / policies grammar, no churning neighbor. With this lock the full v1 module roster (5 required spine + 7 optional) is settled state of record.

## What we ruled out

**The lighter per-PR Review-record disposition for accepting an advisory** (rejected — the operator chose §15; an `allow-*` entry durably loosens security coverage for all future PRs, so it is a guardrail weakening deserving the one deliberate acknowledgment gesture, not a per-PR note that a standing coverage hole rides past on a routine click). **Re-implement the §15 acknowledgment gate inside the module** (rejected — the module relays into the existing control-plane §15 gate and owns only its allow-list semantics + committed config, the §16 detection/mechanism split; re-owning the gate would duplicate locked machinery). **Frame the private-repo unlock as a free settings toggle** (rejected — platform-false: dependency review on private repos requires the paid GitHub Code Security add-on, ~$30/active-committer/mo; the disclosure names it as a real cost/benefit purchase, never a toggle). **Home the allow-list as a free-floating `.github/` dependency-review-config file** (rejected — that is a coherence-orphan, the [D-135](0135-re-verify-the-three-d-132-d-133-unblocked-modules-resolve-gi.md) class; the allow-list is the dependency-review check's own committed `params`, homed in the module's `check` provides). **Ship a third-party dependency-review Action into product CI** (rejected — the detection relays GitHub's native first-party data, REST API or GitHub's own published Action, introducing no third-party supply-chain surface; R5). **Expand the locked §15 guard's monitored set to name the module's allow-list** (rejected as litigation-unnecessary — the guard's "check definitions" scope is categorical and already covers it; the only build-spec demand is that the classifier read an allow-list addition as weakening-direction, additive within that scope). **Edit catalog/architecture/glossary/risks to mark the lock** (rejected — floor only; design-maturity not catalog-tracked and R1 subsumes the residual).
