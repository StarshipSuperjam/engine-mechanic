# Construction-scaffold flexibility for AI stepwise-build failure modes: coping-deferral disclosure, dependency preference, grouped fixes, coupling-sized build units; reject feature-integration branches

*Decided 2026-06-03 in the design workspace.*

## The decision

The operator named the recurring AI stepwise-build failure modes — a forward-referenced piece silently made **optional / prose / brittle** because a later slice does not exist yet, with no path back; **dependency-avoidance** producing brittle in-house reinventions (a JSON stand-in in a YAML corpus); and per-PR **ceremony swamping work**. The remedy is *not* a feature-branch model but four changes to the **non-locked `core-build-roadmap` construction scaffold** (no locked engine doc touched): (1) a **coping-deferral disclosure** standing rule — every weakening-to-ship is declared in the PR body and filed as engine-labeled tracked debt naming the consuming slice that must undo it (an `owes →` pointer), distinct from a planned Leaf, with a clean slice asserting "nothing weakened to ship"; (2) a **dependency-preference** standing rule — adding the optimal substrate (a real parser, a real schema validator) is the preferred path, not a last resort, with a per-slice `Prefer` pointer where the source implies a tool, and the uv-runtime discipline unchanged; (3) a **grouped-fixes** section — corrections to merged slices ride grouped multi-commit fix builds at proportionate / fast-path depth per the locked [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) law, never one-fix-one-full-harness-PR; (4) **coupling-sized build units** — the build unit is right-sized by coupling (a Plan-time judgment the locked build-orchestration already grants: *"chosen at Plan by size/risk and how tightly the work couples"*), folding tightly-coupled mutually-defining slices into one revisable draft PR so cross-definition surfaces *before* merge. A cold-context reclustering + **dry-run build simulation** (29-agent workflow: 3 coupling-proposers → reconcile → per-cluster derivability + adversarial surprise lenses → synthesis) produced a sound **K1–K12** coupling clustering and found *every* current roadmap entry **non-derivable** from under-specification — validating the operator's concern with named instances and raising one locked-doc **litigation alarm** (see the deferred anti-choice). **Propagation:** the three standing rules + the `Prefer` entry-shape field were written into `wbs/core-build-roadmap.md`; this entry. `python3 validate.py` green; no locked doc touched.

## Why

The constraint that was biting is a *non-locked scaffold default*, not an engine law. The locked model is **one PR = an ordered, revisable commit sequence** ([build-orchestration](../spec/systems/lifecycle/build-orchestration.md)) — the orchestrator is the single writer who rewrites commits on the draft-PR branch (force-push is blocked only on the protected branch) before submit — so "revise a bad early choice before it merges" already exists at PR granularity. The roadmap's *"every slice is one PR against protected main"* was a Builder-A convention (an explicitly transient scaffold, no `stub|designed|locked` status), and it is what merged a wrong early guess to `main` sessions before its consumer surfaced it. Right-sizing the build unit by coupling, disclosing coping deferrals at the moment of the choice, and preferring the right tool attack all three failure modes within the locked grammar. The dry-run is the project's own build-readiness gate (`CLAUDE.md`) applied to the reclustered plan.

## What we ruled out

**Feature-integration branches** (a long-lived `feature/*` accumulating slice PRs, then one admission PR to `main`) — rejected: it breaks the **M1 self-bootstrap** (the engine must be operative *on `main`* to build itself), forces a big-bang integration PR a **non-engineer cannot consent to** ([principles §17](../principles.md)), reintroduces the close-friction the design deliberately removed ([D-038](0038-session-lifecycle-re-founded-on-native-substrates.md)/[D-122](0122-enumerate-the-branch-ruleset-protection-floor-in-control-pla.md)), and does not even solve the far-apart-coupling case it is invoked for; the flexibility it sought is already reachable by build-scope sizing. **Generalizing the dependency-preference / deferral steers into locked principles or policies** — rejected: kept to the construction scaffold per the no-generalize-a-steer-into-a-law discipline; a *deployed-engine* "prefer the optimal dependency when building products" disposition is a separate, operator-unraised question, left untouched. **Writing the K1–K12 clustering into the roadmap now** — deferred, not rejected: the dry-run found the entries non-derivable, so the clustering write-in and the entry-derivability rewrites are gated behind resolving the surfaced **S-8 litigation alarm** (slice 12 / K1: the machine-readable-policy-values mandate has no carrier because the locked [policies](../spec/systems/surfaces/policies.md) + [templates](../spec/systems/guardrails/templates.md) docs shipped a *prose* carrier — a locked-doc change requiring the litigation protocol and operator approval) and a re-run dry-run, tracked as the active follow-on.
