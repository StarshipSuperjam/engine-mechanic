# Correct the falsified "platform ignores a `PreToolUse` deny" claim: live-verified deny is honored across built-in and MCP tools (litigation alarm + authorization)

*Decided 2026-06-05 in the design workspace.*

## The decision

A claim baked into the locked corpus as "verified" — that *"the platform ignores a `PreToolUse` deny for some edit paths"* — is **falsified by live behavioral testing on current Claude Code** and is corrected. Two operator-runnable ([§17](../principles.md)) behavioral tests on this platform supply the evidence:
  - **Test 1 (built-in tools):** a `PreToolUse` deny emitted as **exit-0 + a `hookSpecificOutput` `permissionDecision:"deny"` wrapper** — the exact format [hooks](../spec/systems/infrastructure/hooks.md)' `hooks.py` produces — is **honored** for `Bash` and for `Write` (a file mutation, the gate's primary target); non-deny calls pass through.
  - **Test 2 (MCP tool):** the same deny format is **honored for an MCP tool call** (`mcp__filesystem__read_text_file`) — the hook fires for the MCP tool, matches, and the call is refused; instrumented controls confirmed the hook live (a marker `Bash` blocked) and non-denies passing. So MCP tools are **not categorically exempt** from `PreToolUse` deny on this platform.
  - **Provenance of the retracted "verified":** the historical "ignored" reports it rested on trace to **implementation errors / non-reproduction, not platform behavior** — #37210 (exit code 2 + flat/unwrapped JSON read as a hook crash → the deny dropped; resolved NOT_PLANNED as a caller bug), #18312 (an explicit `permissions.allow` entry short-circuiting the hook — DUPLICATE; inapplicable, as the engine allow-lists no gated tool), and #33106 (the MCP path, closed by a stale-bot and **not reproduced** by Test 2).

  **This entry is the litigation alarm + authorization** (the operator approved the audited change-set); the **re-locks land under the resolve entry** after the mandatory landed-text cold audit — the [D-169](0169-add-the-foundational-eadr-canon-the-engine-ships-its-own-why.md)→[D-170](0170-resolve-the-d-169-foundational-eadr-canon-re-litigation-land.md) pattern. A four-lens cold **plan**-audit (adversarial · technical-feasibility · non-engineer-operator · architect) ran against the proposed correction and reshaped it before this authorization (it surfaced an MCP residual and a multi-carrier blast radius, both then resolved — by Test 2 and the carrier sweep below).

  **Design (final, post-plan-audit + Test 2):**
  - **The design is unchanged; only a cited *example* is retracted.** The fallibility **law** stands ([D-070](0070-lock-the-modes-system-wave-3-head-three-stances-on-two-axes.md)'s "uniformly fallible §6 nudge; the only unbypassable wall is the protected-branch merge"); what was false is one of its cited grounds (deny-ignored-for-edit-paths). The "uniformly fallible" conclusion is **re-grounded** on the surviving, durable limits — **fail-open** (a crashed gate lets the action through; the [hooks](../spec/systems/infrastructure/hooks.md) law; applies to every leg) and **best-effort shell-verb detection** (a shell string is not fully parseable — aliases / `eval` / substitution / chaining evade it; the Bash leg) — not on a brittle platform-version claim. The MCP path is **not** named as a limit (Test 2 shows it honored, not a gap).
  - **No leg is dressed as "reliable."** Even an honored deny rides a hook that can crash (fail-open), and a local gate is never the wall — so [D-070](0070-lock-the-modes-system-wave-3-head-three-stances-on-two-axes.md)'s rejected "tool-name legs reliable, only Bash best-effort" framing **stays rejected**, and the §6/§7 closer ("never claims any leg of it is reliable") is preserved. The deny mechanism is a *stronger* nudge than the old text implied (it does not silently lose denies), but a nudge still.
  - **The locked docs carry no platform-version-specific "verified" claim.** The durable structural truth (fail-open + shell best-effort + merge-wall-is-the-only-wall) lives in the locked docs; the dated live-verification evidence lives here in the log — so a future platform change cannot re-falsify a locked doc (the lesson of this very correction).
  - **Editable locked carriers corrected (this change-set):** [modes](../spec/systems/lifecycle/modes.md) (delete the false limit; re-ground the gate-fallibility paragraph on fail-open + shell-best-effort; preserve the §6/§7 closer) and [hooks](../spec/systems/infrastructure/hooks.md) (the `:77` premise *"blocks only on exit code 2"* → *"blocks on exit code 2 **or** a `permissionDecision: deny`"*, the path the Engine uses — a precision fix reconciling `:77` with the doc's own contract section, the fail-open conclusion unchanged). Operator-scoped to fix both in one pass.
  - **Append-only carriers named as superseded (NEVER edited — history exceptions):** the false claim also appears as a supporting aside in **[D-031](0031-integration-debt-is-a-telemetry-owned-register-not-a-knowled.md)** (the harness-disposition deny caveat), **[D-051](0051-guardrail-integrity-the-builder-cannot-silently-weaken-its-o.md)** (rationale point 4 + anti-choice — one of four grounds for dropping the standalone `PreToolUse` weakening-guard member) and **[D-070](0070-lock-the-modes-system-wave-3-head-three-stances-on-two-axes.md)** (the modes lock — law 3 + the "uniformly fallible" rationale + the anti-choice). These entries **stand as authored**; this entry supersedes their platform-fact aside. **Their decisions are unaffected:** D-051's member-drop stands on its three other independent grounds (orphaned ownership — natural owner [validation](../spec/systems/guardrails/validation.md) is locked; non-operator-facing; the §15 merge-gate check is strictly sufficient), and D-070's modes laws all stand (allow-by-default, fallible nudge, merge wall, session-scoped stance, operator-only entry). ## Why

A locked trust document stated as "verified" a platform fact that two live, operator-runnable tests on the current platform disprove; leaving it is a direct hit on **auditability** and **trustworthiness** (the operator's own gate would assert a falsehood about the very gate it describes). It is a justified re-litigation, not silent drift — the lock stops drift, not warranted edits — and the four-lens cold plan-audit reshaped the correction before authorization (surfacing the MCP residual, which Test 2 then closed, and the three-carrier blast radius the first single-doc framing missed). The correction *strengthens* the design's honesty without weakening any guarantee: the merge wall remains the only unbypassable wall, every leg remains a §6 nudge (now via fail-open rather than a false platform claim), and the locked docs are made resilient to platform churn by keeping the dated evidence here and only the durable structural truth in the docs.

## What we ruled out

**Leave the locked claim (it is non-load-bearing)** (rejected — a "verified" falsehood in a locked trust doc corrodes auditability; the deletion mandate + §7 require correcting it). **Edit D-051 / D-070 / D-031 to scrub the false aside** (rejected — the decision log is append-only; supersede via this entry, never edit). **Re-introduce the MCP path as a "verified" residual or a new fallibility limit** (rejected — Test 2 shows MCP deny honored on the current platform; naming it a gap would repeat the original sin of baking an unverified, brittle platform claim into a locked doc; #33106 does not reproduce). **Upgrade the tool-name deny legs to "reliable" now that deny is honored** (rejected — §6/§7 + D-070's standing anti-choice; fail-open keeps every leg fallible and the local gate is never the wall). **Trust the closed GitHub issues without a live test** (rejected by the operator — platform facts demand ground-truth on the live platform; the live tests are the §17 gold standard and resolved the MCP question decisively). **Defer the hooks `:77` precision fix to a later pass** (rejected — the operator scoped both fixes into one pass while the context is loaded).
