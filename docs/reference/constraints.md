# Constraints

The hard limits every part of the design must respect. These are not negotiable within v1; they
come from the platforms and the operator, not from our preferences.

## Claude Code

- **Fresh context every session.** No state survives in the model between sessions; durable state must live in the repo (or an out-of-repo substrate over repo-authoritative data).
- **`CLAUDE.md` and auto-memory are context, not enforced configuration.** They inform behavior; they do not guarantee it. Enforcement must come from hooks, validators, and the GitHub control plane.
- **Auto-memory is off-repo and bounded.** Stored under `~/.claude/`, only a small leading slice loads per session. Useful as a convenience cache; insufficient as the citable system of record.
- **`Stop` hooks can block turn completion; `SessionEnd` hooks cannot.** Close gates belong in `Stop`; `SessionEnd` is for cleanup/logging only. A `Stop` block is a *strong local block, not an absolute wall* — Claude Code releases it after a bounded number of consecutive blocks, so a local close gate makes evasion take deliberate effort but the durable, unbypassable gate remains the protected-branch human review.
- **`SessionStart` hooks inject context before the first prompt** — the place to assemble a bounded boot pack **into the model's context**, read by the model, not rendered to the operator (see the operator-channel item below).
- **Hook output is capped, and overflowing it degrades silently.** A hook's output strings — `additionalContext`, `systemMessage`, plain `stdout` — are capped (10,000 characters at time of writing); past the cap the payload is written to a file and **replaced with a preview and a path**, the way an oversized tool result is. The cap binds **each value, not the event's total** — when several hooks return `additionalContext` for one event, all of the values are delivered — so the budget question is always "is *this string* over the cap", never "do these payloads sum past it". Nothing errors and nothing warns. So an over-cap boot pack does not merely lose its tail: it can lose whatever the design relies on being *present* — a grounding marker's absence then reports that the hook never ran when it did, a silent degradation that also misreports its own cause. Any assembled pack must therefore measure itself against the cap and **shed content loudly** rather than overrun ([boot](../spec/systems/lifecycle/boot.md)). The exact cap is a platform figure that may move; the don't-depend posture is that a pack is bounded and self-measuring, never sized by assumption.
- **No hook output channel reaches the operator's screen; the AI's own message is the sole in-session operator channel.** Every hook output — `additionalContext` and plain `stdout` (model context only), `systemMessage` (documented user-visible but field-unreliable), and `permissionDecisionReason`/stderr (not reliably shown) — reaches the model or fails to render, never the operator's normal chat (live-verified). So operator-facing content the engine produces in-session is delivered **only if the AI relays it in its own reply**. This is current-platform behaviour that **may change in a future version** — held with the same don't-depend posture as the field-unreliable compact-source re-injection below; the design's response is the **operator-presentation relay** convention ([glossary](glossary.md)), revisited if a reliable operator-visible channel later appears. (GitHub pull-request and issue bodies stay operator-visible out-of-session.)
- **Compaction has a documented re-injection path, but it is field-unreliable.** After a context compaction `SessionStart` fires with `source: "compact"` and *can* inject `additionalContext`; `PostCompact` is observe-only (no injection, no block) and `PreCompact` can block but not inject. The compact-source injection is **documented but not reliably delivered** (tracked upstream), so the engine must not depend on it for grounding. The root `CLAUDE.md` is re-read from disk and re-injected after a compaction — substantially reliable (a disk reload, not summary-survival), though not airtight — so a post-compaction session leans on that floor plus the next `UserPromptSubmit` scent, never on the compact-source hook alone.
- **Resuming a paused session is a reliable `SessionStart` fire — distinct from compaction.** Re-opening a session (`--resume`/`--continue`/`/resume`) fires `SessionStart` with `source: "resume"`, and its `additionalContext` injection is **reliable** (unlike the field-unreliable `compact` source above) — the hook re-runs so it can refresh context on resume. The full boot pack therefore re-renders on every resume, which is why a standing alarm repeats verbatim across resumes unless boot's anti-habituation collapse intervenes ([boot](../spec/systems/lifecycle/boot.md)). The `source` values are `startup` (new session), `resume`, `clear` (`/clear`), and `compact` (after compaction).
- **`session_id` is reportedly re-issued on resume — evidenced, not established.** A resumed session is reported to receive a **fresh `session_id` UUID** rather than the original's, which would make any hook state keyed on `session_id` (an already-surfaced record, a dedup store) start empty on resume. Held at an explicitly **weak** tier: the report is a duplicate-closed issue with no successor cross-reference, describing a version now many releases old, and the design pass that surfaced it **could not reproduce a resumed chain to confirm it cold**. So it evidences the behaviour without establishing it is current. Nothing in the design may **depend** on `session_id` being unstable *or* stable: where a dedup would be nice-to-have, the engine forgoes it and re-renders (cheap content, no mechanism earned — [boot](../spec/systems/lifecycle/boot.md)); where one already exists, its scope is stated as bounded by the session identifier rather than by the conversation. Re-verify before any design leans on it.
- **Autonomous/scheduled runs cannot ask clarifying questions.** Routine-mode prompts must carry explicit success conditions and finding-routing.
- **Subagents and plan mode** are first-class: exploration and research can run without touching disk.
- **Claude Desktop auto-isolates each interactive session in its own git worktree.** A new session opens in `<repo>/.claude/worktrees/<name>` on a generated branch, leaving the operator's top-level checkout untouched; new worktrees branch from `origin/HEAD` when the remote is reachable (falling back to local `HEAD` offline). This is **per-entry-point and version-contingent**: **Local Desktop scheduled tasks do *not* auto-isolate by default** (they run in the working directory unless the operator enables a per-task worktree toggle), and a manually `cd`-entered worktree can resolve `.claude/settings.json` from the wrong root so engine hooks may not fire there — whereas an auto-isolated session loads its committed `.claude/` normally (hooks fire). The engine **relies on this native isolation** for the operator-checkout boundary ([build-orchestration](../spec/systems/lifecycle/build-orchestration.md), [provisioning](../spec/systems/infrastructure/provisioning.md)) rather than a bespoke guard, held with the same don't-depend posture as the items above — a default, not a guarantee, with the never-strand-main floor and the stranded-checkout detector covering the residual.

## GitHub

- **"Use this template" copies the file tree** (single initial commit, default branch by default) — **not** repository settings.
- **Branch protection / rulesets are settings, not files.** They do not travel with the template; they require a one-time bootstrap on the generated repo (and the default `GITHUB_TOKEN` typically lacks the admin permission to set them).
- **CODEOWNERS and required-status-check bindings only have teeth once branch protection is applied.** Workflows travel and run, but cannot block a merge until a ruleset marks them required.
- **GitHub Actions** supports cron schedules and `concurrency` groups — the host for periodic audits and single-flight routine jobs.
- **The default `GITHUB_TOKEN` cannot create branch protection or a ruleset**, even with elevated workflow `permissions`. Applying one requires repository-administration capability — the classic `repo` scope (which a default operator `gh` login **does** carry) or a fine-grained token with **Administration: write** — so the bootstrap must run as an operator-privileged actor that holds that capability (refreshing to it only in the rare case it is absent), not as the Actions token.
- **The default `GITHUB_TOKEN` cannot read a *separate* private repository** — it is scoped to the workflow's own repo, so a scheduled workflow that must read a *different* private repo (e.g. the self-audit reading the off-repo memory **backup vault**) cannot use it. A **non-interactive cross-repo private read** needs a stored credential: a **fine-grained PAT scoped to that one repo with `contents:read` only** is the least-privilege vehicle (distinct from the broad classic `repo` scope), held as a repository secret. There is **no per-path sub-repo scoping**, so a token for a **shared** vault necessarily reads every namespace in it ([R31](risks.md)) — a per-project vault is the only structural way to scope the read to one project. Personal-account fine-grained PATs may be set to **no expiration** (avoiding a silent yearly stop on an unattended scheduled read); a PAT scoped to an **org-owned** repo is re-capped by the org's max-lifetime policy, so an org-hosted vault re-introduces expiry and relies on the credential-specific re-arm. ([D-241](../adr/0241-authorize-completing-the-audit-s-off-repo-memory-read-enable.md).)
- **A guard can read the per-branch evaluated-rules endpoint** with the default token, but the ruleset-configuration endpoints are admin-gated reads — so a "is protection on?" check must query the evaluated rules, not the configuration.
- **Secret scanning and push protection are free on public repos**; on private repos they require the paid tier. **Dependabot** alerts, security updates, and `dependabot.yml` version updates are free on all repos, public or private.
- **Native code scanning (CodeQL) is free on public repos**; on private repos it requires the paid GitHub Code Security tier. CodeQL **default setup** is GitHub-managed (no committed workflow, auto-updating) and is enabled by an admin-capability call — `PATCH /repos/{owner}/{repo}/code-scanning/default-setup` with `state=configured` (the operator's `repo` / Administration: write, the same capability the ruleset bootstrap uses); on a **free private** repo it fails with a clean, detectable **403** ("Advanced Security is not enabled"), so a caller can branch on the status and skip. Default setup is a *setting* (does not travel with the template) and, when enabled, silently disables any committed CodeQL workflow. (**Advanced setup** is instead a committed `.github/workflows/codeql.yml` that travels as a file, but publishing its results still needs Code Security on private repos.)
- **Private vulnerability reporting is a public-repository-only feature** — structurally absent on private repos (not merely a paid tier). It is free, enabled by an admin-capability call — `PUT /repos/{owner}/{repo}/private-vulnerability-reporting` — and is a *setting*, not a file (does not travel with the template).
- **A committed `SECURITY.md` is auto-recognized as the repo's security policy** with no setting, from the repo root, `.github/`, or `docs/` (ship one location; `.github/` takes precedence). It travels via "Use this template" like any file and is recognized on private repos too — internal-facing there, since the public "Report a vulnerability" intake rides private vulnerability reporting.
- **A template-generated repo's committed workflows do not run on the generation commit** (there is no "repository created" trigger, and "Use this template" lands a single initial commit) and **may land disabled** in the generated repo — so a workflow first runs on the next real push/PR, and provisioning may need a conditional `gh workflow enable`.
- **A pull-request author cannot approve their own PR.** A required-review gate with a sole code owner therefore deadlocks; a required-checks-only gate lets the author merge their own PR once checks pass. Real second-party review needs a distinct AI commit identity.

## MCP

- **MCP servers are out-of-repo processes** the operator must have running. They can fail, and a non-engineer cannot debug them.
- **Trust boundary.** A server that fetches external content is a prompt-injection surface; substrates must operate over repo-authoritative data and be treated as replaceable infrastructure.

## Operator and deployment

- **The operator is a non-engineer who builds *through* the engine, not by reading code.** No step may assume the ability to debug Python, read a stack trace, or hand-edit GitHub settings beyond a single documented command — not because the operator is incapable, but because the engine's trustworthiness must never depend on it.
- **The operator cannot manage a language runtime.** Extending the limit above: no step may assume the operator can install Python, create or activate a virtual environment, run `pip`, pin an interpreter version, or triage a dependency-resolution error. The engine's tools are Python, so any runtime they need the engine must **provision and manage itself** — isolated from, and never mutating or depending on, whatever Python the operator's machine happens to carry. This is a limit to honor, not relax: where that runtime cannot stand up, the engine degrades loud to the committed boot floor, never to the operator's system Python. (Design response: the engine-managed, uv-provisioned tool-runtime — [provisioning](../spec/systems/infrastructure/provisioning.md), [D-156](../adr/0156-name-the-engine-s-execution-substrate-a-group-scoped-uv-mana.md).)
- **The template maintainer/builder is also a non-engineer, and the sole gate-holder from the first commit — with no outside engineer available.** Constructing the engine-template repo is gated by that non-engineer: they direct the build and approve every merge but cannot read code, debug a stack trace, or audit a CI workflow. So no construction step — the seed (stage 0.0) included — may rest on code-reading or an engineer's review. The construction merge gate is **informed consent on evidence, never code review** (principles §6/§15), the same *kind* of gate the deployed operator holds; only the maintainer's latitude differs (full repo ownership, freedom to spend on review depth), not their code-literacy. Confidence is earned from independently-triangulated AI cross-checks, mechanical validation, and behavioral demonstration the non-engineer can run — never from inspecting code.
- **Solo / small-team, no managed enterprise scope.** Org-enforced policy is unavailable; the substitute is project scope plus GitHub branch protection, rulesets, required checks, and CODEOWNERS — strong, but not identical to org-level enforcement.
- **The engine/product wall.** Product code is the adopter's domain; engine assumptions must not leak into it, and product specifics must not leak into the engine surface.
