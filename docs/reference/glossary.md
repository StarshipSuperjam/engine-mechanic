## Terms

- **Engine** — the governance + cognitive apparatus shipped by the template, living under `.engine/` and `.claude/`, *by* which a product is built. It is a contributor to the product, not a component of it: the product is built by the Engine, never on it (it carries no dependency on the Engine and ships standalone).
- **Asymmetric awareness** — the rule that the Engine knows the product but the product does not know the Engine; the dependency arrow runs Engine → product only. Generalizes the engine/product wall from separation (of paths and identifiers) to direction of dependency. Removing the Engine degrades AI-buildability but never handicaps the product.
- **Template (the repository)** — the GitHub template repo that, via "Use this template", generates a new engine-equipped project.
- **Foundation** — a non-modular capability present from layer one (repository topology, state, memory, knowledge, attention, templates, validation, telemetry, control plane, hooks, provisioning).
- **Surface** — a named file-type the ontology catalogs, each record carrying a class (prose/structured/code), an authority tier, a lifecycle, a governing schema, and (for prose) a template. Examples: contract, policy, schema, tool, operation, skill, agent. Derived outputs (reports, telemetry, knowledge-graph output) are observational tier-4 *outputs* (system-owned, not catalogued surfaces) that describe rather than govern. Module manifests are not catalog surfaces — they belong to the module-system.
- **Ontology** — the meta-contract and authoring-grammar spine: it names every surface in the catalog and fixes the laws that shape everything authored (amend-first, authority, enforcement, escalation, lifecycle). Amended before any new surface is authored.
- **Meta-contract** — the record every surface declaration satisfies: name, class, location, purpose, authority tier, lifecycle, governing schema, template reference.
- **Catalog** — the single schema-governed data file enumerating one meta-contract record per surface. Its governance fields are authored; its coverage (every surface has a home, no orphans) is derived and gated.
- **Self-referential core** — the three surfaces the grammar uses to describe itself, named in the locked ontology: contract, policy, schema. Every other surface grows additively.
- **Authority tier** — a surface's semantic precedence rank: decisions (contracts) ▷ standing rules (policies) ▷ mechanics/guidance ▷ derived/observational. Higher wins; same-tier or ambiguous conflicts escalate.
- **Contract** — the decision-record surface (an ADR): one architecturally significant decision with rationale and anti-choice. Top authority tier; file-per-decision; append-only in a deployment's own stream, while the shipped canon is revised in place (the engine's eADR-0014). Two engine-namespaced id schemes on the `eADR` root — the engine-owned canon `eADR-####`, a deployment's per-instance stream `<project-slug>-eADR-####` — so an engine record never collides with a product's own ADR system, nor the two engine streams with each other as the Foundational eADR canon advances.
- **Foundational eADR canon** — the bounded set of `eADR-####` Contracts the template *ships* (the engine's own structural-law *why*), distinct from the per-instance stream a deployment accumulates under its own `<project-slug>-eADR-####` namespace. Engine-owned and overlaid on upgrade (the per-instance stream is deployment-owned and preserved); law-selected from the founding structural decisions, kept stable by construction — a living cold-copy snapshot revised in place under its eADR-0014, never accumulating routine decisions — and reached on demand — the [§18](../principles.md) rationale-transplant, not an ADR pile. Maintainer vocabulary.
- **Policy** — the standing-rule surface: an ongoing directive (second authority tier). The v1-core policies are contract-threshold, finding-disposition, escalation, and triage-threshold.
- **Specification** — a current-state design document (rewritten in place), ratified by a contract and possibly locked; not itself a contract.
- **Check** — the check-rule surface: one declarative validation rule (`id`, `target`, `kind`, `params`, `tier`, `suites`, `message`, plus the optionals `status`, `ci_author_exempt` — the pull-request authors a rule does not bind in CI, resolved to a disclosed not-applicable no-op — and `ci_label_exempt`, the label-keyed sibling carve-out, e.g. the engine-erasure label), authored as data the validator dispatches, never as validator code.
- **Check-suite** — a thin trigger-bound collection of checks (name + trigger + execution context); its roster is *derived* from the rules that self-declare into it, so a module install never edits a central list.
- **Check-kind** — a callable in the validator's registry that evaluates a class of checks; a closed core set (schema, shape, presence, coverage, coherence), extended by modules that **provide a conforming callable, discovered by presence** ([derived binding §14](../principles.md)), plus a `custom/script` escape hatch. Bound by presence but **not an [interface](../spec/systems/surfaces/interfaces.md)** — a dangling kind fails to a finding, it has no fallback.
- **Operation** — the procedural-body surface: the authoritative steps of a multi-step engine procedure performed by reading-and-following, referenced (not restated) by its skill/agent invokers — one procedure, one home. Distinct from `tool` code, an `agent` persona, and a specification; earns standalone status only as a shared body (≥2 referencers) or a human-in-loop runbook, an audit-judged anti-sprawl bar.
- **Skill** — the in-session procedure surface: a Claude Code `SKILL.md` (progressive disclosure), living in `.claude/skills/` (tool-dictated), engine-prefixed by convention. *Who invokes it* is the `invocation` axis: `model-auto` (the model loads it on a description match; the operator may also type it, **but not at a cold start** — a model-invocable skill is absent from the `/` menu until after the first message, [D-200](../adr/0200-authorize-the-status-verb-cold-start-re-litigation-model-aut.md)), `operator-typed` (operator only, `/engine-…`, typeable from a cold start; `disable-model-invocation: true` — what an operator calls a *command*), or `model-only` (`user-invocable: false`). Model-invocable values carry an always-resident name+description (the attention cost → ship few/sharply-described); operator-typed carries none but must be discoverable. Distinct from the spawned [agent](../spec/systems/surfaces/agents.md) and the shared [operation](../spec/systems/surfaces/operations.md) body.
- **Command** — the operator's plain word for a verb they type, e.g. `/engine-build`. Realized as a [skill](../spec/systems/surfaces/skills.md) with `invocation: operator-typed` (`disable-model-invocation: true`; the legacy `.claude/commands/` form also works) — not a separate surface. Thin, delegating to an operation (one procedure, one home); engine-prefixed by convention (`/engine-…`); a plain-language discovery path is a committed v1 requirement.
- **Interface** — the protocol-contract surface: the stable callable boundary a swappable implementation satisfies, naming its own default/fallback (degradability stated at the contract; an active fallback is surfaced to the operator). Implementations bind by presence and **resolve single-active** — exactly one answers; more than one non-default present is a coherence finding, never a silent pick (distinct from the set-valued roster/suite cases). Distinct from a `schema` (data payload) and from wiring (shared-state edits). v1: `search`, knowledge representation/retrieval.
- **Tool** — the code surface (`.engine/tools/`): the engine's executable machinery (validators, hooks, MCP servers, the wiring library, interface implementations). Class `code`, so it carries no governing schema and no template — governed by tests and checks.
- **Doc** — the operator-facing-documentation surface (`.engine/docs/`): hand-authored plain-language explanation for the operator (the AI orients from derived output, not docs). Lives in the engine corner, never the product's root; anti-drift via the audits cold-context random-target probe. v1 ships at least one operator orientation doc.
- **Conduct** — the operator-stance surface (`.engine/conduct/`); its instances are *codes of conduct*: standing, plain-language behavioral expectations for how the AI engages (dialog, pushback, provenance-before-decisions, plain-language, not fragmenting trivial fixes), present from cold boot in every repo and tunable. Tier-3 *guidance*, **posture** enforcement — it shapes behavior, never enforces or gates (whispers, not walls), subordinate to every contract/policy/mechanical guardrail. Two committed layers: universal **defaults** shipped in [core](../spec/modules/core.md) (overlaid on upgrade) beneath an **operator override** (operator config, preserved across overlay, **seeded at provisioning from the maintainer's template seed** so the operator's stance travels without re-teaching), composed **per-rule by `id`** (not policy's numeric per-key merge). Loaded at the grounding floor via the root `CLAUDE.md` `@import` (hook-independent, so it survives a boot-hook failure); **bounded** because it is paid every session. The deployed-Engine home for what this workspace's own collaboration stance does — the cold-boot counterpart to [memory](../spec/systems/cognitive/memory.md)'s per-project enrichment (the transcript-first record and the operator's pins), and authored via an engine-mediated [core](../spec/modules/core.md) verb, never a blind hand-edit. ([D-192](../adr/0192-authorize-the-conduct-surface-codes-of-conduct-a-tier-3-pros.md).)
- **Derived binding by presence** — the discovery axis ([principle §14](../principles.md)): the engine discovers *which* providers/implementations/members are present by their presence and self-declaration (the agent roster, check-suite membership, interface implementations, workflow activation), never a central list an install mutates — distinct from the closed wiring seam, which makes keyed reversible edits to shared state.
- **Derived-committed artifact** — a committed file whose *entire content is a deterministic function of the committed source tree* (same tree in → byte-identical out): the [§19](../principles.md) class. v1 members of the built integrate reconciler: the [knowledge](../spec/systems/cognitive/knowledge.md) graph (`graph.json`) and the [ontology](../spec/systems/grammar/ontology.md) self-map. The [product-design](../spec/modules/product-design.md) spec-obligation matrix shares the class's defining property (source-deterministic — one row per settled acceptance criterion, regenerated from `docs/spec/`) but is **not** in the reconciler's member set: its refresh is the product-design commit-boundary hook, with the CI drift gate as the durable backstop, so a concurrent conflict on it is surfaced for a regenerate-and-commit rather than auto-cleared. **Instructive non-members:** the surface catalog (governance fields authored, only its coverage derived — a conflict is a *real* authored conflict), the audit digest (run-dated + judgment-bearing, so not source-deterministic), and version-state — the engine manifest `engine.json` (per-instance install state) and `uv.lock` (resolved against the external package index, not the committed source tree alone). Distinct from the *tier-4 derived output* the Surface entry names (reports, the gitignored knowledge index/boot-slice): a derived-committed artifact is committed canonical *structure*, a tier-4 output is an observational cache. Because generation is source-deterministic, a concurrent-PR merge/rebase conflict on a member is **spurious** — resolved by **regeneration from the reconciled tree**, never a hand-merge, never surfaced to the operator to resolve ([D-024](../adr/0024-the-engine-is-upgradeable-versioned-packages-upgraded-by-ove.md)); the [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) orchestrator regenerates members at `integrate` (the [§16](../principles.md) relay: knowledge/ontology own the generators, integrate relays). Membership is by property, not a frozen list. Every member also carries its Artifact warrant (the [§7](../principles.md)/[§17](../principles.md) humility on what a green result shows). Maintainer-layer vocabulary.
- **Artifact warrant** — the [§7](../principles.md)/[§17](../principles.md) discipline (name the tier honestly; confidence bounded by a non-AI correlate, with the bound *stated*) applied to a *generated artifact* — any machine-produced output whose correctness depends on derivation logic (a derived index, map, graph, digest, coverage report, or check verdict, committed or not). A plain-language statement, surfaced **where the artifact is trusted**, of (1) what a valid result **shows**, (2) what it **does not show**, and (3) **what review still has to check** — the third named honestly: where the consumer can corroborate it themselves (run a check, spot-check the output against its source) it says how, and where the residual is an authoring/review-time judgment they cannot re-run it says *that* plainly rather than inventing a step they cannot take (never "verify the derivation logic"). It is **proportionate** (the same three-part shape; most prominent where the bound is least obvious, light where self-evident — uniform disclaiming that trains the consumer to skip warrants is the failure it guards against). For a [§19](../principles.md) derived-committed artifact an *embedded* warrant must itself be **derived** (byte-identical for one source tree), never authored; otherwise it rides the consumption surface; a transient gitignored cache **inherits** its committed source's. **Presence** is by-construction for a committed artifact, **posture** for a surfaced rendering (optionally a structural shape-check, never a word-filter — [§12](../principles.md)); **accuracy** is the per-PR build-conformance review's, with the [audits](../spec/systems/guardrails/audits.md) prose-probe catching register/jargon drift. The class is broader than the [§19](../principles.md) source-deterministic committed subset (the audit digest and a surfaced check verdict carry a warrant though they are §19 non-members). The **sibling of Negative fixture**: that proves a `hard` check *bites*; this states what a *green* result does and does not show — the two halves of check honesty. An *unrun* check the warrant points to is a **promise, not proof**, and an **offer for when the change matters, not a duty on every merge** ([D-252](../adr/0252-authorize-binding-the-17-operator-runnable-behavioral-correl.md)). Maintainer-layer vocabulary; the operator meets only the plain-language line, never the word "warrant."
- **Travel-safety** — the first-run *reference-closure* invariant ([provisioning](../spec/systems/infrastructure/provisioning.md) retire phase, its definition-of-record): no file that **survives** first-run retirement may statically reference a **retired** first-run asset — by `import`, `importlib`, a subprocess invocation of its path, or a hard-coded read of a retired file's path. A survivor needing such machinery is itself a first-run asset (retired with it) or is removed; there is **no guard exemption**, because a static check cannot certify a guarded reference keeps a generated repo's first CI green. Enforced by a hard CI closure check ([validators-core](../spec/modules/validators-core.md) rule-data, [validation](../spec/systems/guardrails/validation.md) coverage); anchored in the [repository-topology](../spec/systems/infrastructure/repository-topology.md) "What travels" law. Distinct from the Derived-committed artifact class (source-determinism of what *ships*, not safety of what *survives a deletion*). Maintainer-layer vocabulary. ([D-219](../adr/0219-authorize-the-first-run-travel-safety-re-litigation-a-retire.md).)
- **Deferral seam** — the ownership axis ([principle §16](../principles.md)): at a seam between two systems, *detection* of the upstream condition and the upstream *mechanism* stay with the owning substrate, while the integrator binds to the seam's stable *channel* and relays — it surfaces, ranks, deduplicates, or gates *over* the channel but owns neither which upstream owners exist nor what they detect (boot surfaces what state/memory/control-plane detect; telemetry acts on findings cognition emits; attention ranks what its substrates own). The sibling of **derived binding by presence** ([§14](../principles.md)): §14 is *which providers are present*, the deferral seam is *who owns what across a boundary*; both are distinct from the closed wiring seam. The payoff is a lighter propagation web — a new upstream item attaches additively and an owner's later settling cannot force the integrator's. Maintainer-layer vocabulary (the [§12](../principles.md) leak guard applies; operators never see it).
- **Lifecycle (surface)** — one of two vocabularies a surface follows: `decision` (proposed → accepted → superseded) or `artifact` (active → deprecated → retired).
- **Finding-disposition** — the rule that every concern the AI surfaces takes a durable disposition (fix in line / log an issue / escalate) and never dies in a chat aside.
- **Module** — an installable capability bundle (the same unit as a *package*; `status` distinguishes `required` / `default-on` / `optional` / `experimental` / `retired`). Declares the files it *provides*, the *wiring* it requires, its dependencies, and its status. The operator-facing *optional* modules are presented at install grouped under module categories; `required` modules are core and are never an install choice ([D-067](../adr/0067-operator-facing-module-packaging-industry-discipline-categor.md)).
- **Module category (operator-facing)** — the install-time grouping of the *declinable* modules under recognized SDLC discipline umbrellas (IEEE 1012 / SWEBOK) — **Product Management, Software Configuration Management, Verification & Validation** — chosen as durable categories that scale to many future modules. A presentation device (provisioning selection-UX data keyed by module `id`), **not** a manifest field and **not** a new install grain. The install walkthrough enumerates only the declinable packages — the opt-out-able optionals plus the `default-on` semantic layer; the core/`required` spine — including the routine *stance* (Mode) and self-checkups (`audit-library`) — is never presented as a choice and is disclosed in the project README ([D-067](../adr/0067-operator-facing-module-packaging-industry-discipline-categor.md)).
- **Slot** — the *fillable* subset of core: a core capability that accepts an optional Filling and runs as a disclosed no-op when none is installed (the [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) gate with no review lenses; the `search` [interface](../spec/systems/surfaces/interfaces.md) on its named fallback). Most core exposes no slot — it simply runs (provisioning, telemetry, modes, close, knowledge). *What is core at all* is set by [§12](../principles.md) (contagious-by-nature) + [D-067](../adr/0067-operator-facing-module-packaging-industry-discipline-categor.md) (always-on, off the install menu), **not** by the no-op property; the operational test is *remove every module — what survives is core, what disappears is a module*. Maintainer-layer vocabulary (the [§12](../principles.md) leak guard applies; operators never see "slot"). ([D-069](../adr/0069-core-module-seam-walk-the-demarcation-operationalized-glossa.md).)
- **Filling** — a module that fills a Slot, discovered by presence ([§14](../principles.md)): a review lens ([design-review](../spec/modules/design-review.md)/[qa-review](../spec/modules/qa-review.md)), or the semantic layer ([memory-semantic-recall](../spec/modules/memory-semantic-recall.md)) whose meaning-based recall operation the one memory implementation registers when the module is present — an added operation beside the `search` fallback floor, never an override ([interfaces](../spec/systems/surfaces/interfaces.md)). A strict *subset* of Modules — the other v1 modules ([product-design](../spec/modules/product-design.md), [dependency-discipline](../spec/modules/dependency-discipline.md), [migration-discipline](../spec/modules/migration-discipline.md), [external-contribution](../spec/modules/external-contribution.md), [github-projects-sync](../spec/modules/github-projects-sync.md)) are standalone optional capabilities that fill no core slot. A filling the operator always installs (their self-host MVP) stays a filling; operator selection never redefines what is core. Maintainer-layer vocabulary. ([D-069](../adr/0069-core-module-seam-walk-the-demarcation-operationalized-glossa.md).)
- **Wiring** — the side-effects a module install must apply beyond copying files: hook registrations, MCP server registration, ontology entries, permissions, gitignore lines, and the Codex runtime's hook/MCP siblings. Declared in the manifest; reversible and keyed. (Check-suite membership is *not* wiring — it is derived from the check files the module provides.)
- **Closed seam vocabulary** — the fixed, reviewed set of wiring directive types a module may declare — seven kinds: `hook`, `mcp`, `ontology-entry`, `permission`, `gitignore`, and the Codex runtime's `codex-hook`/`codex-mcp` siblings — each with a paired applier and reverser in the wiring library. There is no `custom/script` escape hatch for wiring: a module cannot invent a new kind of shared-state side-effect. A new seam type is a reviewed change to the core, and that friction is the firewall against irreversible install effects (Risk R5).
- **Engine-namespaced-identity keying** — how the wiring library makes edits to shared files reversible: an engine entry is identified by its engine-namespaced identity (a hook `command` pointing into `.engine/`; an engine-prefixed MCP server name; a comment-fenced engine-managed block in `.gitignore`), not by a free-floating content match. Apply inserts iff absent; reverse removes only the engine-identified entry, leaving an operator's or product's own identical-looking entry untouched.
- **Tool-runtime** — the engine-namespaced, uv-managed Python environment in which all engine [tool](../spec/systems/surfaces/tools.md) code executes (the validator dispatcher, hook scripts, MCP servers, the wiring library): a committed `.engine/pyproject.toml` + `.engine/uv.lock` (foundation infrastructure artifacts, engine/product wall) materialized by uv sync into a gitignored `.engine/.venv/`. Because uv manages a pinned standalone interpreter itself, the engine neither depends on nor mutates the operator's system Python — avoiding the global-pollution / PEP 668 `externally-managed-environment` failure that would strand a non-engineer ([principles §5](../principles.md)). Materialized by provisioning at first run and re-synced on every engine upgrade; if it cannot materialize the engine degrades loud to the [boot](../spec/systems/lifecycle/boot.md) floor (never to the system Python), accepting that the engine is then inoperable until it can. Maintainer-layer vocabulary (the [§12](../principles.md) leak guard applies; operators never see "tool-runtime").
- **uv** — the Astral Python package-and-project manager the engine uses to own its tool-runtime: a single self-contained binary requiring no pre-existing Python, which resolves dependencies, pins and downloads a managed standalone interpreter, and creates the project environment. **Auto-bootstrapped** by the provisioning instantiator on first run behind an operator consent gate (a heavier trust class than the control-plane OAuth grant — a binary install plus a package fetch), installed PATH-independently to an engine location and invoked by absolute path, its source and version pinned. Maintainer-layer vocabulary (operators never see "uv").
- **uv sync** — the uv command that materializes the tool-runtime's `.engine/.venv/` from the committed `.engine/pyproject.toml` + `.engine/uv.lock`, installing exactly the locked versions. Run **group-scoped** — only the dependency-groups of the installed module set — so a deselected module's dependencies are *resolved-but-not-installed*, preserving "installed means present". Run in CI (group-scoped, via `astral-sh/setup-uv` pinned to a commit SHA) and locally before the dispatcher; on upgrade it re-runs after the overlay replaces the lockfiles and before migrations. Maintainer-layer vocabulary.
- **Dependency-group (tool-runtime)** — the per-module partition of the engine's Python dependencies declared in `.engine/pyproject.toml`: `uv.lock` resolves the **full** set across all groups for one reproducible release, but uv sync installs only the groups **derived** from the installed module set (the check-suite derived-not-wired precedent), so `.engine/.venv/` carries only selected capabilities' deps. A dep-carrying module's group is **named by the module's `id`** (also its `.engine/modules/<id>/` directory name), and `uv sync`'s selection is derived by matching that group name to the present manifest ids under **PEP 735 name normalization**; a module with no Python deps declares no group. The mapping reuses the `id` the manifest already carries — it is **derived, not a manifest field** and not a closed seam vocabulary directive. Maintainer-layer vocabulary.
- **Provisioning** — the subsystem that stands a repo up and installs/updates/removes engine capabilities over its life, by either delivery path (greenfield/brownfield). Two parts: the **instantiator** (one-time, self-deleting) and the **module manager** (permanent).
- **Greenfield adoption** — standing the engine up in a fresh repo generated from the template; the instantiator ships in the copied tree and runs against an empty product.
- **Brownfield adoption** — adding the engine to a live, populated product repo. "Use this template" cannot target an existing repo, so brownfield reuses the engine updater's fetch-and-overlay machinery to place the engine's namespaced files (instantiator included) onto the existing tree, then runs the same instantiator. Mandated by asymmetric awareness / the contributor principle (a contributor joins an existing product). Coexistence is the keyed, additive discipline applied to every platform-shared path.
- **Gather / confirm / apply** — the instantiator's three phases split at one checkpoint (the engine manifest), making first-run resumable without losing choices to a destructive step: a non-destructive re-offerable **gather**, a **confirm** that writes the manifest, and an idempotent manifest-driven **apply** (delete-unselected, render, init, bootstrap). Instantiator *presence* = the repo is unprovisioned (it ships in the template tree, so a "Use this template" copy carries it and re-enters setup). The **provisioned verdict keys on that presence, never on the committed manifest** (which travels with a copy): instantiator present → unprovisioned; instantiator absent **and** manifest present → provisioned; instantiator absent **and** no manifest → a broken/partial checkout routed to the operator-checkout strand detector. The manifest is the apply-resume checkpoint and upgrade source-of-truth — a done-vs-broken disambiguator, not the verdict ([D-277](../adr/0277-litigate-engine-template-353-first-run-dead-on-arrival-in-a.md)).
- **Overlay-install** — placing or replacing only the engine-namespaced paths of a tagged engine release onto a repo, preserving operator config (including any operator policy-override) and gitignored data; the shared mechanism behind both an engine upgrade and brownfield adoption.
- **Operator policy-override** — a committed, per-deployment **operator config** file (preserved across engine overlays — the [memory](../spec/systems/cognitive/memory.md) backup-pointer precedent, not template machinery) that supersedes specific *tunable* values of a `core`-owned [policy](../spec/systems/surfaces/policies.md) for that deployment, merged **per-key over the shipped default at read time** (an unset or stale key falls back to the default). Scope is tuning values only — [attention](../spec/systems/cognitive/attention.md)'s budgets/weights/thresholds and the [triage-threshold](../spec/systems/surfaces/policies.md) values, **never** the structural precedence/trim order or any enforcement config — so it retunes *within* the policy's laws, never weakens them, and stays **determinism-safe** (a static input; [§15](../principles.md) untouched). Set via an engine-mediated authoring command, never a hand-edit; absent until the operator sets one. The deferred [Q17](open-questions.md) auto-calibration would write through this lane. ([D-167](../adr/0167-take-up-q17-component-a-authorize-a-five-foundation-re-litig.md).)
- **Required package** — a foundation expressed as a versioned package (`status: required`): always present, never optional, but versioned and migratable like any module. The whole engine is versioned packages, which is what makes it upgradeable rather than only configurable. A foundation is expressed as its *own* required package only when it owns non-regenerable per-instance data (so its schema needs an owned migration unit) or a seam another package binds to; otherwise its files ride `core` ([D-086](../adr/0086-cognitive-foundations-as-required-packages-reconciliation-me.md)). So `memory-substrate-sqlite-fts5` is its own required package (the gitignored NDJSON ledger + the `search` seam), whereas the [knowledge](../spec/systems/cognitive/knowledge.md) foundation — committed entities + a regenerable index — rides `core`.
- **Engine manifest** — a committed config file recording the engine release the repo runs, each installed package's version, and the engine's **home repository** — the coordinate the updater resolves the release source from and the escalate-upstream audit files against (the same "template repository"), seeded from the template's committed manifest and carried into every generated repo; the source of truth for upgrades. Operator config **preserved** across an upgrade (updated in place, never overlaid wholesale), so the home persists.
- **Engine updater** — the permanent module manager acting as the upgrade path: it resolves the release source from the engine's **home repository** recorded in the manifest (never the deployed repo's own `origin`), pulls a tagged release from **its** GitHub releases, overlays only engine-namespaced paths (code replaced, config and gitignored data preserved), runs migrations, coherence-checks, and lands a reviewed PR; it degrades to the current version when the source is unreachable, and refuses cleanly — with a plain-language reason and next step — when no home is recorded.
- **Update source (release channel)** — the engine's **home repository**'s GitHub releases, the pinned source the engine updater pulls versions from; **which** repository that is resolves from the engine manifest's home coordinate, not from any git remote (a generated repo is detached — no upstream remote — so engine improvements arrive through the updater, not `git pull`, and never from the deployed repo's own `origin`). Distinct from the fork-native **product-project upstream** (Upstream (two senses)), which is never the update source.
- **Release-cut (version production)** — the maintainer-layer process by which an engine version is *produced*, the complement to the consumption-side Engine manifest/Engine updater/Update source (release channel): a **bump rule** (a mechanical floor — new `migrations` ⇒ ≥ minor, a module added ⇒ ≥ minor, a module removed ⇒ ≥ major — plus *unconditional* maintainer confirmation against a plain-language change inventory, the breaking-vs-additive call discharged on an AI-authored impact statement + behavioral demo rather than code-reading ([§17](../principles.md)); the contract-silent breaking change is the named ([§7](../principles.md)) residual) and a **release-cutting mechanism** (a `workflow_dispatch` GitHub Actions cut: signal-diff → propose-with-evidence → confirm → control-plane release PR → tag + Release at the reviewed merge commit, every cut gated on the acceptance-benchmark). A **standing** process, not a construction-QA instrument; its first invocation is the v1 cut (`0.0.0-dev` → `1.0.0`) and the post-v1 engine-mechanic inherits it. Design settled at [D-194](../adr/0194-resolve-q36-the-engine-release-cut-version-production-proces.md) (its source document lived in the retired planning workspace). Maintainer-layer vocabulary (the [§12](../principles.md) leak guard applies; operators see only one engine version vX→vY).
- **External contribution** — the operating arrangement in which the Engine contributes to a product repo the operator does **not** own (an open-source project, or the engine-mechanic); a third arrangement beside greenfield/brownfield, which co-locate the Engine with a product the operator owns. Realized fork-native; product changes reach the un-owned upstream as a product-only cross-fork pull request gated by the upstream's *own* review. Packaged as an optional module ([D-102](../adr/0102-cross-repo-external-contribution-as-a-first-class-v1-operati.md)).
- **Fork-native** — external contribution's realization: the operator forks the upstream (owning the fork) and the Engine is brownfield-installed into that fork, so the fork is an ordinary same-repo deployment carrying the full committed substrate; only product-path changes are submitted upstream, the Engine's committed files never riding the contribution (the §6 upstream-clean nudge, not branch topology, is the guarantor).
- **Engine-mechanic** — the self-hosting special case of external contribution: a deployed Engine instance whose *product* is the engine-template repo itself, which it builds and submits pull requests to. The **separate-workspace variant** (its product is a *checkout* of the template, not a fork it installs the Engine into), **non-reflexive** (engine ≠ product). Its trust base is the engine-template maintainer's own ratification gate ([D-103](../adr/0103-cross-repo-design-cold-audit-resolutions-engine-clean-branch.md)): it runs only a released, ratified engine to build the next and never self-upgrades to its own un-reviewed output, keeping self-improvement clear of the trusting-trust trap ([D-102](../adr/0102-cross-repo-external-contribution-as-a-first-class-v1-operati.md)). It stands up as the **post-v1 build locus**, distinct from the in-repo self-construction threshold (M1) at which construction first leaves the genesis build; both timings are settled ([D-107](../adr/0107-author-the-wbs-module-build-order-the-builder-crossover-reso.md)). Maintainer-layer build-process vocabulary (the [§12](../principles.md) leak guard applies; operators never see it).
- **Upstream (two senses)** — kept distinct: the **engine-update channel** (the update source the updater pulls releases from — a generated repo is *detached* from it, no `git pull`) versus the **product-project upstream** of fork-native external contribution (the repo being contributed to, used only for contribution, never for engine updates).
- **State** — temporal "where am I": the committed cursor read first each session. Pointers and counts only — standing-situation pointers plus a debt count/pointer — not a work inventory or narrative.
- **Standing-situation pointer** — the project's "where we are" (the current phase + milestone), **assembled read-only by [boot](../spec/systems/lifecycle/boot.md) from native sources** — `phase` from the engine's most-recently-merged tracked build Issue, `milestone` from the open GitHub Milestone set under [state](../spec/systems/cognitive/state.md)'s selection bound (GitHub names no *active* Milestone, so the bound is a design rule and state owns it: the one where exactly one is open, all of them named where several are, `none set` where none are — the engine elects none of them, [D-315](../adr/0315-amend-d-314-correct-its-operator-authorship-premise-the-buil.md)) — derived live when GitHub is reachable, so it cannot silently rot. State's committed copy is a **best-effort offline cache** (the debt count's sibling, rendered with the same `as-of`/"may be stale" provenance), **never advanced by any session**: [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) produces the GitHub artifacts the projection reads but writes nothing to it. The offline cache (both fields together, never split) is refreshed by the shared GitHub-derived-cache pass and **committed by the [audits](../spec/systems/guardrails/audits.md) digest pass as freight** — schema-gated, not drift-gated, and a missed cron only ages the labelled copy, never the live read (concrete wiring deferred to the [audit-library](../spec/modules/audit-library.md) build). Honest bound: `phase` is engine-derivable (strong); `milestone` is **read as found, never elected** — its Milestones are engine-planned where a build-plan drives the build and operator-kept otherwise, but either way the field states which are open rather than inferring a current one. ([D-198](../adr/0198-authorize-correcting-100-where-we-are-is-assembled-read-only.md); committer pinned [D-205](../adr/0205-authorize-pinning-the-offline-cache-committer-the-audit-dige.md); selection bound [D-315](../adr/0315-amend-d-314-correct-its-operator-authorship-premise-the-buil.md).)
- **Memory** — narrative "how did I get here": decisions, pushback, lessons. Experiential, per-instance, local. The project's institutional recall — distinct from Claude Code's built-in auto-memory (a non-authoritative personal cache). Heritage: CoALA *episodic memory* (see Lineage).
- **Memory ledger** — memory's canonical form: an append-only NDJSON text file (the SQLite/FTS5 store is a derived, replaceable index rebuilt from it). Append-only governs *live writes*; the record-set is folded forward by **ledger compaction** (below), never edited in place. Makes backup/portability "copy/rebuild" and keeps the retrieval engine swappable.
- **Migration snapshot** — the **retained, pre-migration copy** of the memory ledger, kept as a distinct `refs/tags/…` tag in the backup vault that the **routine rolling backup never overwrites** — distinct from that rolling export, which keeps one overwritable slot per namespace. Written before a data migration reshapes the ledger; [memory](../spec/systems/cognitive/memory.md)'s restore contract has a **migration-revert mode** that targets it when [boot](../spec/systems/lifecycle/boot.md) surfaces a code-older-than-data mismatch. It carries its pre-migration ledger-generation (so the resurrection guard still applies) and is pruned only once no such mismatch can still cite it; the operator meets it only as "the copy saved before the last update," never the tag string. ([D-264](../adr/0264-authorize-git-native-retention-for-the-pre-migration-memory.md).)
- **Memory role vocabulary** *(retired)* — the once-designed closed set of memory roles (decision, rationale/pushback, lesson, dead-end, preference, intent, observation) the curation layer stamped when typing a record. Retired whole with that layer by the transcript-first refoundation ([memory](../spec/systems/cognitive/memory.md)): a `role` an older engine wrote survives as an inert label on legacy records, and nothing writes or filters on one. Open project tags remain — capture stamps transcript/session tags, and free topic tags stay admissible on pins.
- **Ambient capture** — appending session-id-tagged turn deltas to the memory ledger every `Stop`, so content survives an ungraceful session end; cheap (an append, not a summarization). Under the transcript-first model the delta **is recall content** — [the transcript is the layer recall surfaces](../spec/systems/cognitive/memory.md), not fuel for a later curation pass — resident and recoverable in the ledger; harness-injected pseudo-turns are the exception — resident and recoverable, but left out of the rejoined read so machine-inserted text is never mistaken for something the operator said.
- **Deferred consolidation** *(retired)* — the once-designed pass turning raw ledger deltas into curated episodic records at a tolerable moment (`PreCompact`/close, or a boot-time abandoned-delta sweep). Deleted whole with the curation model by the transcript-first refoundation ([memory](../spec/systems/cognitive/memory.md)): `PreCompact` now triggers only deterministic ledger compaction, no AI consolidation runs anywhere, and the transcript itself is the recall-eligible layer. Gists an older engine wrote survive as ordinary legacy records.
- **Frecency** *(retired)* — frequency × recency, the once-designed usage signal by which memory would have ranked records for cued, recurring recall. Deleted with the curation lifecycle ([memory](../spec/systems/cognitive/memory.md)): there is no frecency and no per-record score of any kind; a rare-but-critical record is protected by **recoverability** (compaction folds and prunes deterministically, and erases only on audit-adjudicated, merge-consented evidence), never by a ranking.
- **Ledger compaction** — memory's self-directed whole-ledger rebuild-and-swap (memory's own restore primitive applied internally): it folds redundant transition records into current-state fields and prunes the hot index (reversible, autonomous), and physically erases a record (or an enumerated batch of records) only once the [audits](../spec/systems/guardrails/audits.md) loop has adjudicated each and the operator has merged a single-purpose erasure PR. Crash-safe (same-directory temp → fsync → atomic rename → directory fsync → generation-stamped full index rebuild). Bounds growth without a second store. *Archived* is an index-exclusion **state**, not a separate store — the record stays resident in the one ledger.
- **Operator-adjudicated erasure** — memory's hard-delete evidence class for a record the [audits](../spec/systems/guardrails/audits.md) loop recommended and the operator removed by **merging a single-purpose erasure PR**; distinct from *operator-directed* (the operator pointing at a specific record). Enacted cross-session — a later local session observes the merge and appends one idempotent erasure marker **per named target**, keyed by the merge identity; the committed Issue/PR references each target by a **stable, content-free record id** (never quoted ledger content, never an offset). A single erasure PR may name **one or more** records; its merge consents to the whole enumerated set, each shown by its plain-language cost — never a bare total.
- **Knowledge** — structural "how does this world work": what exists and how it relates. Purely derived from source surfaces; does not carry debt. Heritage: CoALA *semantic memory* (see Lineage).
- **Attention** — "what to focus on, at what level": a committed prioritization *policy* plus a deterministic ranking *function* (it holds no store of its own) that budgets what orientation surfaces and orders the candidates within each budget partition — the work among them being the in-flight branches/pull requests and the open engine-labeled debt (never the operator's backlog or the project's plan; that ordering is the build-plan's, [D-314](../adr/0314-litigate-engine-template-394-attention-s-work-record-commiss.md)). Powers every orientation event. The engine's instance of the *context engineering* discipline (see Lineage).
- **Boot pack** — the bounded orientation assembled at cold start (`SessionStart`) from committed state, the surface grammar, and (when available) the substrates; prioritized where it surfaces ranked items. It **measures itself against the platform's hook-output cap and sheds its lowest tier with a relayed notice rather than overrunning** — a **posture** chain, not a guarantee ([§7](../principles.md)): the hook must fire, the guard must measure, the AI must relay, and each link is fail-open. The heaviest member of the orientation event family. Heritage: CoALA *working memory* (see Lineage).
- **Recognition slice** — the cut of the [surface catalog](../spec/systems/grammar/ontology.md) the boot pack carries: the **recognition fields** (name, location) of *every* surface definition, and none of the governance fields (authority, lifecycle, `governing_schema`, template), which are the pull-request author's business and not a cold session's. It is the grammar a session recognizes a file-kind by, so it is a step-2 **input** read before ranking, never an [attention](../spec/systems/cognitive/attention.md) ranking candidate — outside that partition by construction, since attention partitions candidates. Re-rendered whole on every pack render (no dedup — a few hundred characters never earned a mechanism), and first to shed under the cap guard, because recognition is **posture and fail-open**: losing it degrades to the same state as a hook that never fired. ([D-309](../adr/0309-litigate-the-grammar-and-boot-cluster-ledger-grammar-core-u0.md).)
- **Orientation event family** — the set of cognition-refresh moments (cold-start boot pack, the per-prompt scent, post-compaction re-orient, close), each read-only and powered by Attention, budgeted by "latency while building is tolerable, while using is not."
- **Scent** — the cheap lexical pointer the `UserPromptSubmit` hook injects every prompt: an *attributed, unverified* "memory/knowledge has notes on X — verify before asserting," turning consultation from pull (the model must remember to look) into push. Silent on no strong match; fail-open and de-duplicated. An *active / forward-looking retrieval* push (see Lineage).
- **Debt register** — the **view over open engine-labeled GitHub issues** (marked per the [control-plane](../spec/systems/infrastructure/control-plane.md)-owned engine-label scheme), the telemetry-owned home of tracked engine self-monitoring debt (the locked finding-disposition "issue scaffold"); an issue references knowledge entity-ids for "what is broken." Not a committed file — native, citable, disk-loss-proof, and upgrade-safe. State holds only a count/pointer; Attention surfaces it; knowledge never carries it.
- **Lineage (design heritage)** — the cognitive substrate is not novel cognitive science; it follows recognized work, cited so the design stands in traveled lanes rather than re-deriving them. **These labels are maintainer-layer vocabulary only — like "microkernel-inspired" ([D-025](../adr/0025-fault-containment-is-earned-at-the-seams-not-conferred-by-mo.md)), they must never appear in operator-facing surfaces or runtime narration; operators see plain language.**
- **CoALA** — *Cognitive Architectures for Language Agents* (Sumers, Yao, et al.): the descriptive framework whose taxonomy the substrate follows — *working memory* (the boot pack / orientation context), *episodic memory* (Memory), *semantic memory* (Knowledge — its *structure* only; CoALA-semantic is belief-bearing, but belief lives in Memory's record — the transcript and the operator's pins — never the derived graph), and a *decision-making procedure* (modes + attention + boot). CoALA leaves semantic-memory representation open (examples span unstructured text to structured stores; retrieval sparse or dense), which licenses the swappable index. Followed as taxonomy, never implemented as a spec.
- **Context engineering** — the named discipline (Anthropic) of deciding what to load, exclude, prioritize, and prune in the context window; the orientation family instantiates it, with Attention as its prioritization piece.
- **Active / forward-looking retrieval** — the proactive-retrieval pattern (e.g. FLARE: retrieve on low-confidence tokens within an anticipated future sentence) the Scent instantiates — with the difference that the Scent triggers on a lexical match against the user prompt, not token-confidence prediction.
- **Telemetry** — the mechanical, continuous detect-and-surface layer of Engine-only self-monitoring; derives streams from native records (merged-PR CI via `gh`, best-effort ambient check fires, the memory ledger), triages signals into engine-labeled issues, and feeds the remediation loop. Counts and trends; never judges (that is Audits).
- **Remediation loop** — detect (telemetry) → triage (open/update a deduped engine-labeled issue) → surface (next boot, via Attention) → remediate (an AI Build PR, editing engine content not machinery) → validate (the fix's CI + the debt's clearing signal); auto-close when the signal stays clear. Closes across sessions; never heals unattended.
- **Audits** — the judgment, periodic rung above telemetry: a purpose-built cold-context, read-only persona that gives the **deployed Engine an anti-entropy tune-up**, asking "is the running engine still *fit*, or has it accumulated local cruft no rule can catch?" under an adversarial/retirement-default posture — **and, where a `docs/spec/` is locked, whether the product still conforms to that frozen spec** (the standing cadence of the Conformance-enforcement floor, conditional and per-locked-row, report-only, silent absent a locked spec — [D-296](../adr/0296-litigate-engine-template-427-residual-three-l1-l2-l3-audits.md)). Acts on **accumulated local state** (template-owned machinery, told apart mechanically by manifest `provides` membership, is escalate-upstream-or-immutable — never a local retire-candidate) and on **product conformance to the locked spec** (a forward divergence-hunt over the locked rows via product-design's Spec-obligation matrix, read by presence — no `depends`, silent absent a locked spec); reports and recommends via the two **disposition lanes** below; never remediates autonomously. It weighs a retire/keep call with **its own prior digests** (the dated digest history) as over-time corroboration — persistence sharpens the case, a fresh function-probe still decides it ([D-233](../adr/0233-authorize-the-audit-over-audit-re-litigation-feed-the-period.md)). Ships no maintainer-style systemic-architecture review of the *template's* engine architecture (distinct from the product-conformance sweep) and no self-tuning ([D-076](../adr/0076-lock-the-audits-system-re-founded-for-the-deployed-repo-hygi.md)).
- **Disposition lanes (audits)** — the two routes an audit finding takes: **local retire/reconcile** (accumulated local cruft → ordinary Build work, operator merge = adjudication) and **escalate-upstream** (a template-machinery bug → a drafted report below).
- **Escalate-upstream** — the disposition for a finding about template-owned **machinery**, which a local PR cannot fix (the next engine overlay reverts it). The audit *drafts* a bug report for the template repository — the engine's **home repository**, the coordinate from the engine manifest the updater also resolves the release source from (one coordinate, two readers) — and surfaces it; the operator files it via their own `gh`, forks, or ignores — never auto-filed, never a silent phone-home, deduped by stable source-key, degrade-and-disclose if unfilable. An additive elaboration of the locked `escalate` finding-disposition ([D-076](../adr/0076-lock-the-audits-system-re-founded-for-the-deployed-repo-hygi.md)).
- **Concern-entry** — a row of the audit concern-list: a `target`, an `adversarial-question`, its `finding-types`, and a `justification` (the affirmative case for the row). Growth is bounded by deliberate reviewed authorship (added via a merged Build PR) + a schema presence gate + reflexive function-probe retirement — no numeric cap.
- **Audit posture laws** — the three stances that make audits worth having: adversarial/retirement-default (preserve only with an affirmative case; ≥1 retire-candidate), function-probe-not-stats (claims rest on a content probe run now, not cached counts), and the cold-context random-target probe.
- **Audit digest** — the committed, fingerprint-gated, plain-language snapshot an audit run produces: the Engine's self-attestation of its own operational health, openable by a non-engineer (the self-map precedent). It **carries its run-date**, so a digest-staleness check can surface a stopped audit cron at boot ("the engine hasn't self-reviewed in N days") through the locked open-findings path — closing the silent-stop gap on the operator's return. Its own committed history (the dated digest sequence) is read by later audits as **over-time corroboration** — evidence a thing has *stayed* unfit, never the decider ([D-233](../adr/0233-authorize-the-audit-over-audit-re-litigation-feed-the-period.md)). A system-owned, non-surface derived output. It carries its Artifact warrant at consumption — the in-corpus exemplar of the discipline ([D-261](../adr/0261-establish-the-artifact-warrant-discipline-a-7-17-application.md)).
- **Function probe vs liveness** — a *function probe* asks "does this still do work?" and is an audit-time judgment; *liveness* asks "is the substrate up right now?" and is owned by boot degradation + hooks fail-open. Neither is a standing telemetry daemon.
- **Triage-threshold policy** — the governed [policy](../spec/systems/surfaces/policies.md) holding telemetry's promotion thresholds (severity-class sets latency: trust-critical promotes immediately, persistent-benign on a threshold) and the triage-pressure threshold, kept legible and tunable rather than buried as constants; the **fourth v1-core policy** ([D-114](../adr/0114-q25-re-litigation-a-fourth-v1-core-policy-the-triage-thresho.md)), foundational to telemetry's operation rather than the trust model.
- **Triage-pressure stream** — the telemetry stream that counts open low-severity engine-labeled issues and surfaces one plain-language boot line when its (policy-housed) threshold is crossed. **Render-only** — it never itself promotes to an issue, so the meter cannot feed the volume it measures. It is the *visibility* half of the volume story; the actual bound on triage volume is **structural** — the dedup key is the signal's source identity (rule/surface/stream-id), never per-occurrence, so under telemetry's Engine-only scope every recurrence collapses onto one issue and open volume is bounded by the engine's own finite signal-source inventory, not a numeric cap ([D-075](../adr/0075-lock-the-telemetry-system-guardrails-arc-head-the-triage-vol.md)).
- **Control plane** — the GitHub layer that enforces review and checks: workflows, CODEOWNERS, branch protection / rulesets.
- **Engine-label scheme** — the [control-plane](../spec/systems/infrastructure/control-plane.md)-owned contract for marking GitHub Issues as the engine's own: a single **engine-domain label** applied to every Issue the engine creates (its presence means engine-owned, its absence ordinary product backlog — the subject-of-claim split decided at [D-039](../adr/0039-reports-self-improvement-scope-engine-only-self-monitoring-o.md)). The product spec is **not** in this scheme — it is a committed [`docs/spec/`](../spec/modules/product-design.md) corpus, not an engine-labeled Issue ([D-244](../adr/0244-re-litigate-product-design-into-a-first-class-spec-driven-de.md)); product-design's decomposed work Issues are ordinary un-labeled backlog. The Debt register is a view over the label; consumers read it by its presence and never mutate it, and it is the **channel discriminator** the [engine-Issue-conformance reroute gate](../spec/systems/lifecycle/modes.md) scopes on ([D-235](../adr/0235-authorize-the-engine-issue-conformance-reroute-gate-promote.md)). Concrete label strings and the apply mechanism are deferred build-spec leaves ([D-132](../adr/0132-own-the-engine-label-scheme-in-control-plane-re-litigation-r.md)).
- **Engine-authored-issue body contract** — the [control-plane](../spec/systems/infrastructure/control-plane.md)-owned *body shape* for the GitHub Issues the engine creates programmatically (which bypass the human issue templates entirely): a loose plain-language skeleton — *what it is and why it is here* / *what the operator must decide, or what happens next* / *backstage references as links, never an id dump* — that each producer's own operator-contract language fills (the PR-contract tiering: the shape's presence is the floor, its truthfulness is posture). The sibling of the **Engine-label scheme** on the same engine-labeled channel. Realized **by construction** through a single shared issue-authoring helper producers call, with routing-through-the-helper for the **engine-labeled channel** enforced by a **`PreToolUse` reroute gate** — a minimal-work-loss redirect that denies a non-conforming engine-labeled creation and points to the helper (GitHub cannot gate creation server-side, so the lever is client-side, backstopped by an `on:issues` CI check; the shape's presence is the gated floor, its truthfulness still posture, [§6/§7](../principles.md)). Pinned at [D-184](../adr/0184-resolve-the-d-183-issue-authoring-grammar-correction-landed.md), gated at [D-235](../adr/0235-authorize-the-engine-issue-conformance-reroute-gate-promote.md). Maintainer-layer vocabulary (operators meet only the legible Issue, never the term).
- **Engine-Issue-conformance reroute gate** — the [control-plane](../spec/systems/infrastructure/control-plane.md)/[modes](../spec/systems/lifecycle/modes.md)-owned **`PreToolUse` block** that denies a non-conforming engine-labeled `gh issue create` (or issue-creating `gh api`) and redirects the session to the issue-authoring helper, making the **Engine-authored-issue body contract**'s routing a gated floor rather than bare posture. A **minimal-work-loss redirect** — it loses no work (the Issue still gets filed, via the helper), so it earns its place in the [hooks](../spec/systems/infrastructure/hooks.md) block budget without being governance-critical ([§6](../principles.md)); **scoped to the engine-labeled channel** (unlabeled/human Issues and the escalate-upstream draft are exempt); fallible and fail-open, with **no merge wall behind it**, so its only catch-all is the `on:issues` CI backstop. Authorized at [D-235](../adr/0235-authorize-the-engine-issue-conformance-reroute-gate-promote.md). Maintainer-layer vocabulary.
- **Enforcement tiers** — hard-fail (mechanical, unbypassable), soft-warn (advisory), posture (expected but unenforced).
- **Hook** — a Claude Code event binding that fires an engine script at a session lifecycle moment (`SessionStart`, `PreToolUse`, `PostToolUse`, `PreCompact`, `Stop`, …); registration lives in committed settings and travels with the template.
- **Block budget** — the law that only `PreToolUse` and `Stop` may hard-block, and only for an enumerated set of governance-critical invariants; every other hook nudges or injects.
- **Fail-open-and-flag** — when a hook gate crashes, the guarded action proceeds (never stranding the operator) but the failure is promoted to a finding and surfaced to the operator in plain language; it never fails silent.
- **Operator-communication law** — operator-facing surfaces explain clearly and completely and never simplify away substance (the *substance* edge), **and address the operator as the capable adult they are** — never condescending, never a register pitched below them, never explaining at length what they plainly already grasp as if they could not (the *register* edge). The edges are **orthogonal**: a surface can be complete and accurate yet still fail by *how it addresses the reader* — talking down while hiding nothing. Because informed consent requires understanding, and a reader talked down to is being managed, not informed. The register edge is the rubric the [audits](../spec/systems/guardrails/audits.md) cold-context doc-probe reads a doc against, so a condescending doc is **surfaced for remediation rather than passing unexamined** — the audit tier (a recommendation the operator adjudicates), not a hard gate, but no longer invisible to review. The **substance** edge also governs **jargon**: clarity over needless jargon — the right word for the operator's need, with a term the operator needs explained — is part of *never engineer-shorthand*, **realized by judgment, never a banned-word list**: no word is forbidden and **no forbidden-word list may be created** (a list invites list-growth and teaches that word-banning is a writing function). Whether prose leans on jargon is a **semantic judgment** the same doc-probe and the per-PR build-conformance review own, **never a mechanical word filter** ([§7](../principles.md): a substring check grades prose mechanically, which the law forbids). This is distinct from the [§12](../principles.md) leak-guard, which keeps *internal machinery* out of operator narration as a relevance judgment — itself not a vocabulary ban.
- **Operator-presentation relay** — the convention by which all operator-facing engine content reaches the operator: because no Claude Code hook channel renders to the operator's screen (a version-contingent platform quirk — [constraints](constraints.md); the AI's own message is the sole in-session channel), every operator-facing emission is **relayed by the AI in chat, or it is invisible**. Three rules: (1) **injected content is AI-facing** — the boot pack is the AI's *briefing* ("you received this; the operator cannot see it; use it to help them"), never a message written to the operator; (2) the safety/consent-critical subset is **pushed** every session (carried by an imperative relay marker) while routine status is **pulled** on demand (the status verb) — a *pushed standing alarm whose condition is unchanged* collapses to a terse reminder rather than re-relaying in full ([boot](../spec/systems/lifecycle/boot.md)'s anti-habituation, via the standing-alarm presentation ledger), which varies only the *payload behind* the marker, never its presence; (3) the **present-marker** is the **presence of a named orientation block as the AI's first output** each session (it carries a pushed alarm or a one-line all-clear) — a binary "did-I-ground?" check whose *absence* from the AI's opening is the operator's "did-not-ground" signal, never an interpretation of the block's contents; its presence check and the all-clear render never collapse. Honest tier: relay is **posture** ([§6/§7/§17](../principles.md)) — the platform offers nothing stronger; the protected-branch merge backstops governance, and a skipped governance relay shows as a missing present-marker. Defined once here and **referenced** (not restated) by [boot](../spec/systems/lifecycle/boot.md), [modes](../spec/systems/lifecycle/modes.md), [close](../spec/systems/lifecycle/close.md), and [build-orchestration](../spec/systems/lifecycle/build-orchestration.md); the delivery mechanism (AI-as-pipe) is pinned to the quirk and revisited if it changes, while the UX shape (push-critical / pull-routine) is durable. Maintainer vocabulary (the operator meets only plain language and the relayed content).
- **Standing-alarm presentation ledger** — [boot](../spec/systems/lifecycle/boot.md)'s **local, gitignored, non-canonical** anti-habituation marker: per surfaced governance alarm, a fingerprint of its **structured condition** (the per-branch evaluated-rules signal; the open-findings identity set) plus a *shown-in-full* marker, read and written by boot's own `SessionStart` hook. It lets boot **collapse an unchanged standing alarm to a terse, consequence-keeping reminder** and relay a new/changed/worsened one in full — suppressing the *repetition*, never the *signal*. **Fail-toward-full** (a missing/unreadable/ambiguous ledger renders the alarm in full — the safe direction), isolated from memory's own `SessionStart` riders (the erasure observer and the backup export), rooted at a stable per-instance path (never an ephemeral worktree). Orientation's **sole** local write — and no exception to boot's "read-only of canonical state" law, which is scoped to *derived or committed* state and was never in play: a gitignored, non-canonical presentation marker is outside its reach, not carved out of it. Other substrates' writes that ride boot's `SessionStart` moment ([memory](../spec/systems/cognitive/memory.md)'s erasure observer and backup export, [modes](../spec/systems/lifecycle/modes.md)' stance clear, [knowledge](../spec/systems/cognitive/knowledge.md)'s slice cache) are theirs, not orientation's. Never committed, never derived from source, carries no Artifact warrant (a transient gitignored cache inherits its source's). Maintainer-layer vocabulary (the operator meets only the plain-language reminder). ([D-269](../adr/0269-litigate-q18-engine-template-313-resolve-cross-session-anti.md).)
- **Operator checkout** — the **top-level working tree** the operator opens (the repository root on the default branch), distinct from the per-session **worktrees** build work runs in. It is the operator's **surface**, not a build workspace: the engine never mutates its git state as build work (the [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) operator-checkout boundary + the `core` deployed-floor **never-strand-main** rule). On Claude Desktop each session is auto-isolated into its own worktree ([constraints](constraints.md)), so the operator checkout normally sits untouched while sessions work and merge through pull requests.
- **Stranded checkout** — an operator checkout left off its intended state (on the **default branch**, engine files present and current). Three conditions are caught: a **broken** state — a **detached `HEAD`**, or **missing/critically-stale engine files** (no `.claude/settings.json` / `.engine/`); a checkout **parked off the main line** on a **non-default branch** (not broken — the gentlest, offline, day-one signal, collapsing when unchanged); and one **missing merged work** (the consequence-gated, network-gated escalation — on the default branch *or* a parked side branch). Distinct from *ordinary behind* — a bare distance with no felt consequence — which is the **normal** state under the worktree-and-PR model and is **never** alarmed. Caught at boot and **offered a fix** ([provisioning](../spec/systems/infrastructure/provisioning.md) detects and fixes; [boot](../spec/systems/lifecycle/boot.md) surfaces and offers), lossless-or-it-does-not-run; merged-vs-unmerged (`git cherry`, best-effort and advisory) shapes only the offer wording, never its safety. Named *stranded*, not *drift*, so the term itself never implies that ordinary behind-ness warrants an alarm.
- **Imperative relay marker** — the directive embedded in AI-facing injected content that compels the AI to surface a high-impact item to the operator in plain language (e.g. *"INFORM THE USER THAT…"*). **Reserved for the must-push set** — governance-critical alarms, the close-gate finding, a grounding-failure, a [boot](../spec/systems/lifecycle/boot.md) cap-shed notice — so the operator-presentation relay does not become a firehose; routine content carries no marker and is pulled via the status verb. A posture strengthener, not a mechanical gate: it makes the relay as strong as the platform allows, never a wall.
- **Status verb** — the operator-facing, read-only [skill](../spec/systems/surfaces/skills.md) (a `core` verb) that renders the status dashboard **on demand** — the *pull* half of the operator-presentation relay. The built dashboard is headed **Project status** and carries what merged last, the open milestone set, the operator's open-issue count, the engine findings count, the session stance, a **Needs your attention** section — the in-flight work and open engine-labeled debt [attention](../spec/systems/cognitive/attention.md) orders, the ranking [D-314](../adr/0314-litigate-engine-template-394-attention-s-work-record-commiss.md) discussed as *ranked work* — and **Recently shipped**. The engine does not rank the operator's backlog at all ([D-314](../adr/0314-litigate-engine-template-394-attention-s-work-record-commiss.md)): their open issues render as a plain count and link, never an ordering. A **What's next** field lives on the GitHub Projects board — not the dashboard — fed by the top line of this same attention ranking ([decision 0328](../adr/0328-adopt-the-board-s-what-s-next-field-superseding-the-spec-s-b.md), [github-projects-sync](../spec/modules/github-projects-sync.md)). Invocation is **`operator-typed`** ([D-200](../adr/0200-authorize-the-status-verb-cold-start-re-litigation-model-aut.md)): the operator types it — including at a cold session start, the moment the unfiltered view is most wanted (a `model-auto` skill would be absent from the cold-start `/` menu). The AI relays the **same** dashboard whenever the context warrants (e.g. the operator asks "what's next") by running the underlying status tool directly, not by model-invoking the skill — read-only, so the AI may run it freely. Because the operator-typed skill carries no resident description to prompt the AI, this offer-on-relevance cue lives in the AI's standing context (the boot pack / the operator-presentation relay convention), not in the skill. The injected boot pack (the AI's briefing) and the status verb's output (the operator's dashboard) are two renderings of the same data in different tones; its concrete name is a build-spec leaf and it is listed in `/engine-help` and the operator orientation doc.
- **Mode (stance)** — the session's operating **stance**, on two axes (permission posture × attendance): **explore** (default, interactive, engine/product writes gated off), **build** (interactive, the build orchestration), or **routine** (unattended, scope-locked). Distinct from Claude Code's native **permission mode** (`permissions.defaultMode`: plan/default/acceptEdits/…) — a *separate axis* that composes with the stance (a session can be in the Explore stance and the plan permission mode). Leaving explore is a deliberate human act.
- **Native permission-mode default** — the Claude Code permission mode (`permissions.defaultMode`) a fresh interactive session opens in. The Engine recommends **plan** as a safe first-touch inside an Engine-managed repo, but it is **posture/ergonomics layered over the Explore gate, never the guarantee** (the gate + merge wall are; [§15](../principles.md) untouched). Not shipped statically — [provisioning](../spec/systems/infrastructure/provisioning.md) writes it at first run as **operator config** only on adoption: adopting plan by default, offering adopt-or-keep when the operator already runs a different mode, and **writing nothing on decline** so the operator's own setting governs (the *yield*). Preserved across overlays; changed later via native `/config`. A separate axis from Mode (stance); not a Build-entry trigger; Routine overrides it with a non-interactive launch posture. ([D-185](../adr/0185-authorize-a-two-foundation-re-litigation-ship-a-native-plan.md).)
- **Build orchestration** — the multi-agent Build workflow: an orchestrating session opens a draft PR (the claim), plans a commit sequence (written to the build Issue proportionately — required for routine-distributed work, offered for interactive multi-commit builds, otherwise held in-session), runs cold-context agent review lenses at an operator-approved depth, reviews/revises/authors worker output as the single writer, and submits the PR (the close) with the Review record filled. Fixed gate shape (posture, with the merge as the only wall); module-supplied lenses.
- **Agent (persona)** — a persona the engine runs for a trigger, defined as a Claude Code `.claude/agents/` file: the build orchestration spawns a cold-context reviewer or scoped-write worker at a gate (the orchestrator is the session, not a persona), and the `audit-prep` cron runs the read-only self-audit persona as the top-level `--agent` session ([D-133](../adr/0133-type-the-cron-fired-audit-persona-re-litigate-agents-role-tr.md)).
- **Persona template** — the core routing-field grammar an agent fills (`role`, `model-tier`, `permissions`, `output-contract`, plus a `lens` for the review roles only — `worker` and `audit` carry none); `model-tier` is a closed **demand vocabulary** (`judgment`/`mechanical`) describing the work's demand, not a model name, realized by the persona's execution profile; the personas themselves are additive modules.
- **Canonical finding (`finding.v1`)** — the shared structural finding base `{severity, message, location ref (file/line)}` homed on the [schemas](../spec/systems/surfaces/schemas.md) surface, extracted from the agent `output-contract`. Referenced by the agent `output-contract` (the review roles narrow severity to `blocking|serious|nit`; the `audit` role declares its own — [D-133](../adr/0133-type-the-cron-fired-audit-persona-re-litigate-agents-role-tr.md)), the [check](../spec/systems/surfaces/check.md) kind-callable result (a pass/fail verdict wrapping it), and [telemetry](../spec/systems/guardrails/telemetry.md)'s finding-record (extends it with `source-id` + first/last-seen markers). `severity` is a **per-consumer enum** (review vs audit vs check `tier` vs telemetry severity-class — different axes) and a **backstage, never-rendered** field; operator surfaces translate to plain language ([D-113](../adr/0113-core-lock-closure-phase-0-the-build-spec-leaf-form-contract.md)).
- **Execution profile** — the concrete `model` + `effort` a persona declares to *realize* its `model-tier` demand level; persona-owned and platform-passthrough, so a new model release is adopted by changing this config **without touching a locked doc** (the durable grammar names the demand tier; the realization churns). The home of the model-agnostic agent grammar — the durable grammar binds work by demand, never to a specific model ([D-100](../adr/0100-decouple-the-locked-agent-grammar-from-the-model-landscape-m.md)).
- **Derived roster** — the orchestration's agent roster, derived from agents' self-declared frontmatter (the **build-gate roles** `plan-review`/`worker`/`pre-submission-review`) rather than a central list, so installing an agent (a file drop) re-derives it with no wiring (cf. check-suites); a present `audit`-role persona runs for the `audit-prep` cron, not a gate, so it is never a roster member.
- **Audit persona** — the cron-fired, read-only `audit`-role agent the [audits](../spec/systems/guardrails/audits.md) system runs: it inspects *standing accumulated state* (not a proposed change), carries **no lens**, runs at `model-tier: judgment` as the top-level `--agent` session fired by the `audit-prep` cron, and routes findings through the audits two-lane disposition. Partitioned out of the build orchestrator's derived roster ([D-133](../adr/0133-type-the-cron-fired-audit-persona-re-litigate-agents-role-tr.md)).
- **Plan-gate risk assessment** — the **pre-audit** consent-and-coverage surface at plan approval (what this touches → recommended coverage → installed/missing → degraded state → a consequence-named **depth** choice → consent) — **never a cost or time figure**, which the engine cannot know (a made-up number is the false confidence the trust model refuses); the engine's informed-consent surface, not benevolent dictatorship. The lens findings are synthesized into one recommended call plus the trade **after** the audit runs (never raw per-lens verdicts), re-engaging the operator on material findings and always on an unresolved blocking finding.
- **Review record** — the [control-plane](../spec/systems/infrastructure/control-plane.md) PR-contract section recording what review a change received: the depth that ran, the lenses that ran, gate completion, the findings' dispositions, and any post-audit-fix delta, **and the change's operator-runnable acceptance steps** (rendered verbatim from the realized `locked` spec's operator-runnable acceptance criteria, or a reason-named no-op). The judgment-layer record, distinct from the mechanical Validation section; its **presence** is hard-gated by the PR-body completeness check, its **truthfulness** posture; the **review-judgment** part is the operator-uncorroborable stretch while the **operator-runnable steps** are the part the operator can corroborate by running ([§17](../principles.md)); operator-read in plain language ([D-073](../adr/0073-lock-build-orchestration-wave-3-terminal-and-re-litigate-con.md)/[D-252](../adr/0252-authorize-binding-the-17-operator-runnable-behavioral-correl.md)).
- **Design → build → QA axis** — the full arc that brackets [build orchestration](../spec/systems/lifecycle/build-orchestration.md): the [product-design](../spec/modules/product-design.md) front door defines intent + acceptance criteria (the referent), the build implements, and the review-lens roster judges the plan (design stage) and the result (QA stage). Design defines the target; QA proves it was met.
- **product-design (module)** — the operator's intent-to-spec front door and the producer of the QA referent; authors a committed, validated **spec corpus** (`docs/spec/`, `stub → draft → locked`), a build-plan, and product-owned design artifacts (product-principles, an arc42 doc, C4 diagrams, an ADR stream, a Diátaxis tree) as a contributor, product-side of the wall; ships the spec form/coverage/lock-integrity checks but no review lenses ([D-244](../adr/0244-re-litigate-product-design-into-a-first-class-spec-driven-de.md)).
- **Product spec** — the product's current-state specification with acceptance criteria, authored by product-design as a committed, validated **`docs/spec/` corpus** (`stub → draft → locked`, [D-244](../adr/0244-re-litigate-product-design-into-a-first-class-spec-driven-de.md)); the operator's "what to build," the engine-validated-*form* confidence surface a non-engineer can weigh. Distinct from the *Specification* entry above (the engine's own design-document sense) and product-owned, not an engine surface.
- **Acceptance criteria** — the checkable conditions a product spec states for "done", as a **criterion → how-verified table** (each verification typed by who can discharge it — operator-runnable vs engine/CI-internal); the referent the `product-intent` and `spec-conformance` lenses consume, and whose **operator-runnable rows the Review record surfaces at the merge** as the operator's run-it-yourself steps ([D-252](../adr/0252-authorize-binding-the-17-operator-runnable-behavioral-correl.md)).
- **Product ADR** — the product's own architecture-decision stream under the product's numbering (`docs/adr/NNNN-*.md`), authored product-side; deliberately never the engine's engine-namespaced `eADR-####` canon nor a deployment's `<project-slug>-eADR-####` per-instance stream (the Contract entry reserves those distinctions).
- **Review-lens roster** — the v1 set of cold-context reviewer lenses the two build-orchestration gates consume, shipped as two stage-suites: the **design-review** suite (`role: plan-review`: product-intent · architecture · feasibility · risk-governance) and the **qa-review** suite (`role: pre-submission-review`: spec-conformance · usability · technical-integrity · security-governance · divergence-hunter). Grounded in the Engine's own cold-session design audit — a floor, not a ceiling, so the QA suite carries the adversarial lane as its own standing `divergence-hunter` lens beside `spec-conformance` ([D-291](../adr/0291-litigate-engine-template-427-follow-up-q-a-q-b-split-build-c.md)); the QA lenses are judgment above the mechanical validation suite.
- **QA referent** — the product spec's acceptance criteria treated as the authoritative target the design and QA lenses check against; carried in the lens `output-contract`, not the locked PR contract. A build with **no `locked` spec** makes the referent-gated lenses a disclosed no-op.
- **Grounding floor** — the known minimum orientation every session boots with (committed State), degradable-up; what makes explore safe as the default stance.
- **Anti-choice** — a rejected alternative recorded inside the prevailing decision record, with the reason it lost.
- **Deviation** — a point where the prototype diverged from the original proposal; tracked and adjudicated in [prototype-deviations.md](prototype-deviations.md).
- **Engine/product wall** — the boundary that confines the engine to its namespaced corners (exclusively `.engine/`, plus engine-owned keyed entries within shared paths `.claude/`, `.github/`, root `CLAUDE.md`, `.mcp.json`, `.gitignore`) and engine-namespaced instance identifiers (e.g. the canon `eADR-####` and a deployment's `<project-slug>-eADR-####`), leaving the repo root and the product's own identifier space to the product; enforced by CODEOWNERS ownership that is **file-precise** (derived from the manifests' `provides` union ∪ the foundation infrastructure-artifact set), not by quarantining the product — so the engine coexists with a product's own content in a shared path rather than seizing the container.
- **Branch ruleset** — the single GitHub setting on the protected branch carrying both protection rules and the required-status-check bindings. A setting, not a file, so it does not travel and is applied once by the bootstrap.
- **Protection floor** — the set of protection rules a generated repo's branch ruleset must carry, fixed as a contract by the [control plane](../spec/systems/infrastructure/control-plane.md): require-a-pull-request (zero required approvals in solo, one code-owner review in team), required status checks, conversation resolution, blocked force-pushes, and restricted deletion, plus an honestly-named bypass posture (solo can bypass, team cannot). Distinct from the required *check names*, which are derived, and from the **security floor**: the protection floor governs what may merge to the protected branch, the security floor governs secrets, dependencies, code scanning, and vulnerability disclosure. Loosening any floor rule is a guardrail-integrity ([§15](../principles.md)) weakening-class change.
- **Bootstrap (control-plane)** — the one-time application of the branch ruleset on a generated repo by an operator-privileged actor, paired with a committed guard that fails loud until protection is in place.
- **Security floor** — the deployment-scaling guarantee that secret, dependency, code, and disclosure safety are present where the repo's tier supports them and **disclosed, never silently degraded** where it does not. It travels and works on any repo (the committed secret-scan workflow + `dependabot.yml`, plus a seeded operator-owned `SECURITY.md`) and upgrades to native GitHub features where supported: secret scanning + push protection, CodeQL code scanning, and private vulnerability reporting (public repos only). Code scanning and PVR are **native-only where supported** — on a free private repo they are absent by deliberate design (no bespoke third-party scanner), disclosed as a known drawback rather than silently missing. Owned by the [control plane](../spec/systems/infrastructure/control-plane.md); the toggles, the seed, and the disclosures are [provisioning](../spec/systems/infrastructure/provisioning.md) mechanism.
- **Project README (the landing front)** — the repo's root `README.md`, which leads a double life. At rest in the **template** it is the engine's **marketing landing front** — the page a potential adopter reads on GitHub to decide whether to deploy the Engine. In a **generated** repo the root README is the **product's**: at first-run instantiation [provisioning](../spec/systems/infrastructure/provisioning.md) seeds a product-owned **starter** (the writer of the required-spine disclosure, [D-067](../adr/0067-operator-facing-module-packaging-industry-discipline-categor.md)) over the traveled marketing front, but **only iff the slot still holds the engine's recognizable marketing seed** — so a brownfield product README or any later operator edits are preserved untouched, and the engine never re-touches the root after instantiation. Product-owned by default (the engine *seeds*, never *claims* it — [topology](../spec/systems/infrastructure/repository-topology.md) law 2), the seeded-root-file sibling of the `SECURITY.md` seed; the seed/replace is disclosed at first run ([D-213](../adr/0213-authorize-the-human-facing-front-door-re-litigation-the-root.md)). The template's actual marketing copy, banner, and the GitHub description/topics are an operator/maintainer go-to-market task, sequencing-gated behind the replace step ([R26](risks.md)).
- **Identity model** — how the AI's commits are attributed and how the merge gate is enforced: solo (AI commits as the operator; gate is required checks plus an informed-consent merge — the ordinary merge click, while a guardrail-**weakening** change additionally requires the distinct **weakening acknowledgment**) or team (a distinct AI identity makes the operator the enforced code-owner reviewer).
- **Guardrail integrity** — the law ([principle §15](../principles.md)) that the builder may change but never *silently weaken* the Engine's own enforcement. The **guarded set is defined by a property, not a fixed path list** ([D-268](../adr/0268-adjudicate-engine-template-250-the-15-weakening-guard-s-guar.md)): a committed file that *constitutes or configures an enforcement gate* — one whose change could remove, disable, rename, or loosen a check, a permission/enforcement hook, or a branch protection (the enforcement config and workflows, the check and suite definitions, the enforcement *logic* the workflows run, CODEOWNERS, the tool-runtime lockfile **and the engine's home coordinate** (supply-chain siblings — the manifest field selecting which repository executable engine code is fetched from), and the ruleset-affecting files); the engine's **non-gate tooling** (session boot, memory, telemetry, the self-review renderer) is **not** guarded. The concrete roster is a build-spec leaf **derived** from the property and **fail-safe** — an enforcement rule's script is guarded by being present ([§14](../principles.md)), and an uncertain file resolves *as covered*; the guard's own set-defining code is itself in the guarded set, so the guard that detects weakening is not falsifiable by the change it judges. **Narrowing the guarded set is itself a weakening-class change** ([D-207](../adr/0207-authorize-the-dependabot-pr-contract-exemption-a-ci-author-a.md)). A weakening-class change hard-blocks the merge until the operator's informed consent — a distinct, deliberate **weakening acknowledgment**, exactly one act heavier than the ordinary merge click — and is surfaced in plain language naming the concrete protection lost. Tiered honestly: solo = cannot weaken silently (the acknowledgment is a deliberateness lever, not airtight — the engine holds the operator's token), team = cannot weaken at all.
- **Weakening acknowledgment** — the distinct, deliberate operator gesture that satisfies the **guardrail-integrity** ([§15](../principles.md)) hard-gate at the merge: **exactly one** affirmative act beyond the ordinary merge click — a pull-request checkbox or an operator-applied (bootstrap-provisioned, never hand-created) label, never a typed phrase or a command — naming in plain language the concrete protection that weakens and what the AI could then do unwatched. An *input* to the frozen-named, trusted-source §15 guard ([D-051](../adr/0051-guardrail-integrity-the-builder-cannot-silently-weaken-its-o.md)), never a parallel check; its concrete form is a build-spec leaf. The second beat of the §15 consent spine (the plan-gate headline is the first); it makes weakening non-silent and deliberate but, in solo, is not airtight — the engine holds the operator's token, so **team** identity is the structural close ([control plane](../spec/systems/infrastructure/control-plane.md), [D-134](../adr/0134-resolve-q22-pin-the-15-weakening-merge-consent-as-a-distinct.md)).
- **Stage-0 harness** — the hand-built governance scaffold (a retired planning-workspace design) that made constructing the engine-template repo legible and reversible *before any engine module exists*: a protected branch + a seed validator + the PR contract + a construction-governance root `CLAUDE.md`, the same shape as this planning workspace's own governance, progressively replaced by the real modules via the supersession ratchet. Maintainer-layer build-process vocabulary (the [§12](../principles.md) leak guard applies; operators never see it), distinct from the deployed engine's control plane.
- **Seed (stage 0.0)** — the irreducibly-ungated first commit of the stage-0 harness: the trust root no later rail can recover, because the ruleset, the seed validator + its CI job, the PR template, and the PR-body completeness check are all established *before* the gates that would check them exist. A mandatory cold review attests it.
- **Supersession ratchet** — the build-order discipline by which each hand-built stage-0 harness piece is replaced by the real engine module that prefigures it, in module-graph order, until the template reaches the self-construction threshold (M1); the protected-branch human merge gate is the one rung that never retires. Maintainer-layer vocabulary.
- **Self-construction threshold (M1)** — the milestone at which the partially-built engine takes over its own construction: the minimal module subset (repository topology + `core` + `validators-core` + the memory floor + the control plane bootstrap, [D-101](../adr/0101-pin-the-stage-0-self-construction-threshold-to-a-concrete-mo.md)) after which the nascent engine, not the hand-governed genesis build, is the better builder. It is the exit criterion of the stage-0 harness and the point the supersession ratchet completes; construction then carries the rest of v1 in-repo, with the separate engine-mechanic build locus standing up only post-v1 ([D-107](../adr/0107-author-the-wbs-module-build-order-the-builder-crossover-reso.md)). Maintainer-layer build-process vocabulary (the [§12](../principles.md) leak guard applies; operators never see it).
- **Maintainer (template maintainer/builder)** — the party who builds and evolves the engine-template repo and gates its construction. A **non-engineer, the sole gate-holder from the first commit, with no outside engineer** ([constraints](constraints.md)): they direct the build and approve every merge but cannot read code, so the construction gate is **informed consent on an evidence bundle, never code review** ([§17](../principles.md)). Differs from the deployed operator only in *latitude* (full repo ownership, freedom to spend on review depth), not in code-literacy. Also names the vocabulary tier ([§12](../principles.md)) that never reaches an operator-facing surface.
- **Build-conformance review** — the per-PR post-build cold review of *built code against the engine-planning design* (a retired planning-workspace design): independent cold lenses (a conformance reviewer + an adversarial divergence-hunter) the orchestrator ground-truths and adjudicates — the per-PR catch for a *semantic* misread that re-grounding cannot see. The post-build mirror of the pre-build dry-run (it asks *does the build match the spec?* where the dry-run asks *can the spec be built?*), in a harsher regime — the artifact is code the non-engineer cannot read and the adjudicator is the same AI. **Distinct from the shipped `spec-conformance` / `divergence-hunter` qa-review lenses** (Review-lens roster): those lenses judge a *product* build against a *product* spec referent; build-conformance judges the *engine's own* construction against the engine-planning design, and — because the product lenses no-op without a product-design referent — it, not those lenses, covered engine self-construction through v1; post-v1 the [engine-mechanic](../spec/systems/lifecycle/external-contribution.md)'s owned-product arm re-homes that same rigor onto the shipped `spec-conformance`/`divergence-hunter` lenses, pointed at the mechanic's own spec corpus — active only against its `locked` rows, the disclosed no-op until then. Maintainer-layer construction tooling that retired at v1 ([D-136](../adr/0136-re-base-the-bootstrap-trust-model-on-a-sole-non-engineer-gat.md)).
- **Acceptance benchmark** — the pre-release efficacy gate that runs the *assembled, running engine* against expert-labeled fixtures and real non-engineer observation (a retired planning-workspace design): the third and last construction instrument after the dry-run (*is the design buildable?*) and the build-conformance review (*does each built PR match the spec?*), it asks *does the assembled engine actually deliver for a non-engineer?* before the v1 template is published. Five gate classes ([D-085](../adr/0085-record-the-cognitive-substrate-efficacy-scorecard-exercise-w.md)): an attention orientation/ranking fixture, memory/scent retrieval-quality evals, a longitudinal recoverability test, a 100%-required gap-recall test, and an operator-perception battery on true non-engineers. An **evidence-to-maintainer gate** — it produces a per-gate evidence bundle rendered in plain-language consequence ([§17](../principles.md)); the maintainer gates publication on it and may release with a *named, logged* sub-bar gate, never silently below bar. Maintainer-layer construction tooling that retires at v1; distinct from [Q31](open-questions.md)'s standing post-release self-conformance instrument ([D-152](../adr/0152-resolve-q15-author-the-pre-release-acceptance-benchmark-the.md)).
- **Behavioral attestation** — evidence a non-engineer trusts by **running an observable behavior and watching it**, routing around AI judgment entirely: a recipe the maintainer runs (and is coached to vary) and watches a gate fire or block — the empty-PR-body check go red, a weakening diff block the merge. The strongest construction evidence class and the only non-AI one besides mechanical-green ([§17](../principles.md)). Subsumes the seed's mandatory attestation (stage-0 §2) — the seed checklist is behavioral attestation applied to the trust root. Bounded by what has an observable correlate; weakest at the seed, where it cannot confirm a gate is bound and unbypassable ([R15](risks.md)). **Shape:** a demonstration is a **falsification over the real shipped surface — it must be able to fail** (a recipe that can only succeed is not evidence); a thin harness that drives real code (a fake transport, a throwaway directory) is fine, but a **parallel reimplementation of the behavior is the alarm** — it means either the real surface is not exercisable or the demo is theater. **Lifecycle:** a demonstration is construction-phase evidence tied to its PR's claim; it is **retired (deleted) once a permanent regression test covers the behavior, or promoted by an explicit logged decision** to a standing operator capability — it does not accumulate. The construction set retires with the build-conformance harness at v1, and a construction demo does not travel into a generated repo unless promoted ([§13](../principles.md)/[§4](../principles.md)). These are **maintainer-layer construction evidence** about the engine's own build; retiring them is distinct from the deployed operator's own per-change behavioral evidence under [§17](../principles.md), which they do not touch. **The promoted standing class** ([D-231](../adr/0231-promote-the-in-tool-demo-subcommand-as-a-governed-ai-run-sta.md)): the engine's in-tool `demo`/`demo-*` subcommand — a falsification carried *inside* a shipped engine [tool](../spec/systems/surfaces/tools.md), which travels into every generated repo because the tool does (the explicit-logged-decision promotion exercised for the whole healthy population). It is **engine machinery, not an operator entry** — tools are Python the operator cannot run ([tools](../spec/systems/surfaces/tools.md): a tool is engine code, "not an operator entry") — so a `demo` subcommand is **AI-run on demand and operator-*relayed*** in plain consequence-language: an **AI-mediated** evidence tier ([§17](../principles.md)-bounded), weaker than the non-AI maintainer-run class above, whose value is that the deployed session can back a claim by showing the real surface fail when broken rather than merely asserting it; the genuinely non-AI, operator-weighable form of any such behavior remains the **retired regression/CI check** (watched on CI, no AI in the loop). **Governed, not accreted:** every member inherits the **Shape** law above (drives the real surface, must be able to fail, no parallel reimplementation), enforced as **posture** at construction (no standing audits/mechanical demo-shape probe exists) and optionally floored by a `custom/script` [check](../spec/systems/surfaces/check.md) asserting a reachable failure path exists; a subcommand that cannot fail (or reimplements rather than drives the surface) is reclassified or fixed, never kept. Distinct again from the standalone construction `demo_*.py` files and from the deployed operator's own per-change [§17](../principles.md) evidence.
- **Negative fixture** — the committed *seeded bad input* a `hard` [check](../spec/systems/surfaces/check.md)-logic unit is meant to catch, bound to its unit by presence (a naming/location convention) and living in a reserved, glob-excluded, coverage-exempt namespace (test data, not a surface). The [validation](../spec/systems/guardrails/validation.md) **negative-fixture meta-check** runs each in-scope hard logic-unit (each kind callable + each `custom/script` instance; a data rule of a proven kind inherits the kind's proof) against its fixture and asserts the expected `hard` finding by set-membership — the standing, CI-enforced proof that a gate **bites** rather than passing as a green no-op, the up-front enforcing correlate to the [check](../spec/systems/surfaces/check.md) "never-fires → possibly inert" telemetry flag. Honest ceiling ([§7](../principles.md)): it proves a *witnessed* negative trips the check **today**, never completeness against every input or stability under drift; the only admissible carve-out is a unit with no statically-decidable CI failure path (a disclosed not-applicable). Owned across the seam — law/execution-model [validation](../spec/systems/guardrails/validation.md), grammar [check](../spec/systems/surfaces/check.md), rule-data instance [validators-core](../spec/modules/validators-core.md), engine entry point + core-kind fixtures [core](../spec/modules/core.md) ([D-256](../adr/0256-authorize-the-every-hard-check-is-proven-to-bite-re-litigati.md)…[D-260](../adr/0260-resolve-re-lock-core-the-dispatcher-run-one-rule-entry-point.md)). The **check-corpus** counterpart to Behavioral attestation: a demo (a falsification of *evidence about a surface*) stays at its *optional* posture floor ([D-231](../adr/0231-promote-the-in-tool-demo-subcommand-as-a-governed-ai-run-sta.md)), while a *check* — the gate the operator's trust routes through — earns the **mandatory mechanical** standard. Maintainer-layer vocabulary (the [§12](../principles.md) leak guard applies; the operator meets only the plain fact that every safety check is itself tested against an example it should catch, so a check can't quietly pass by doing nothing).
- **Spec-obligation matrix** — a durable, enumerated record of the obligations a spec imposes, one row per obligation, built the knowledge-graph way ([§3](../principles.md)/[§19](../principles.md) derive-don't-hand-author, [D-011](../adr/0011-knowledge-graph-state-is-derived-not-hand-authored.md)) as a **derived-committed artifact plus a coverage check over it** (never obligations enumerated inside a check callable). Each row is **fingerprint-pinned to its source span by a content digest**, so a span edit re-opens *exactly* its rows: for a product [`docs/spec/`](../spec/modules/product-design.md) criteria table (a `shape`-validated structured surface) the key is the **criterion-cell digest at its validated table position** — fully derived, **criterion-granular**; for prose design docs (no criteria table) the key is a **heading-delimited span digest** — span-granular, the enumeration a curated act. The pin is **content-derived, never a stable semantic identity** (a reworded obligation re-opens as changed). It gives conformance a **denominator** (total owed), a **continuous reverse sweep** (which owed rows are *not-yet-built*, carried across sessions), and a **stale-flag** when a span changes. A **derived index, never a trusted second referent**: the human-readable design span stays ground truth and the lens re-derives from it, never from the matrix rows, so it adds no AI-legible surface the non-engineer must take on faith — it closes only the *coverage* residual (is every enumerated obligation actually built), never the *semantic* one ([R16](risks.md)). Its home is build-conformance §4 for the engine self-build; it travels to a deployed product build against its `locked` `docs/spec/` as the [product-design](../spec/modules/product-design.md) coverage leg. The derived, source-pinned rows *are* the *criterion-ID scheme* that lets acceptance-criterion coverage trace at criterion granularity without hand-authoring forbidden structure.
- **Conformance-enforcement floor** — the trio a full spec-conformance regime runs: the **spec-obligation matrix** (coverage denominator, above), the distinct **adversarial `divergence-hunter`** [qa-review](../spec/modules/qa-review.md) lens (default-to-divergent, run beside `spec-conformance` as a second decorrelated cold context — it hunts a semantic misbuild that passes its own tests and a diff-introduced over-build the spec never asked for, build-conformance §8), and the **deployed-environment demonstration harness** (the standing, re-runnable behavioral correlate the operator-runnable acceptance criteria retire into — the [§17](../principles.md) evidence that routes around AI). Maintainer-side it is the engine's own build-conformance instrument, which retires at v1. The **floor — not the instrument — travels** into every deployed repo as the [SDD (product-design)](../spec/modules/product-design.md) module's enforcement layer, pointed at the product's own spec (never engine-planning, [§13](../principles.md)) and **conditional on a `locked` `docs/spec/`**; with no locked spec it stays the charitable disclosed-no-op, so the floor never blocks a staged or MVP product the operator scopes ([§20](../principles.md)). It runs at **two cadences over the one matrix**: the shipped [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) `spec-conformance` path **per-merge** (introduction-time, gating at the merge), and a **standing** report-only re-sweep on the [audits](../spec/systems/guardrails/audits.md) cron ([D-296](../adr/0296-litigate-engine-template-427-residual-three-l1-l2-l3-audits.md)) that catches conformance **drift after merge** — the latter running the matrix + the audit persona's own forward divergence-hunt (not the demonstration-harness leg, which stays the operator-run behavioral correlate).
