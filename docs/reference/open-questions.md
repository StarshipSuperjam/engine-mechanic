## The open questions

- **Q11 — Which frontier representation/retrieval engine (if any) to swap into knowledge/memory.** The cognitive substrate keeps the representation/retrieval leaf swappable behind a stable interface ([D-033](../adr/0033-ground-the-cognitive-substrate-in-established-standards-line.md)); v1 is plain per-surface JSON + FTS5 lexical. Candidate swap-ins from the 2025–26 graph-memory research frontier: **MAGMA** (arXiv:2601.03236 — multi-graph: semantic/temporal/causal/entity), **MemOS** (arXiv:2507.03724 — unified memory OS with retrieval + scheduling), **SYNAPSE** (arXiv:2601.02744 — episodic-semantic via spreading activation, whose sparsity/inhibition also bounds [R8](risks.md)'s hub-explosion). Commit to none now; evaluate in the knowledge/memory component sessions. *This is the only doc that names these systems — they churn, and it is deleted on resolution; durable docs name only the swappable seam.*

- **Q17 — A future optional self-tuning module (telemetry-driven auto-calibration).** The deployed-Engine *auto-tuning* ambition — re-weighting [attention](../spec/systems/cognitive/attention.md) prioritization and re-tuning [telemetry](../spec/systems/guardrails/telemetry.md) promotion thresholds (the [triage-threshold policy](../spec/systems/surfaces/policies.md)) *from a project's own observed usage* — is distinct from the now-locked [audits](../spec/systems/guardrails/audits.md) *hygiene* and is deferred to a future **optional** module ([D-076](../adr/0076-lock-the-audits-system-re-founded-for-the-deployed-repo-hygi.md)), out of required core ([§12](../principles.md)). Its **substrate is already designed-in** ([D-167](../adr/0167-take-up-q17-component-a-authorize-a-five-foundation-re-litig.md)): the determinism-safe, per-project [operator policy-override](glossary.md) of tuning values and its committed-operator-config lane are core, so auto-calibration would *write through* that existing lane rather than needing a new one. What remains open is the **learning** half — **usage-fit sensing** on honest best-effort proxies plus an **evidence-sufficiency gate** (tune only on sufficient usage, never a cron-window blip) — and, load-bearing, it **must first resolve the contradiction with [attention](../spec/systems/cognitive/attention.md)'s locked determinism** ("no decay state, no machine learning"): auto-calibration introduces a *learned, mutable* value source where the manual override is merely another *static* input. The scope bound holds — the tunable values are attention's budgets/weights/thresholds and the triage-threshold values, never the structural precedence/trim order or any enforcement config; the build-review-depth default is *not* in this class (a per-build operator choice with a memory-preserved preference, [build-orchestration](../spec/systems/lifecycle/build-orchestration.md)). Pursued only with real multi-project evidence.

- **Q21 — The concrete agent execution realization and the Dynamic-Workflows substrate.** The locked agent grammar binds work to its *demand* (`model-tier` ∈ {`judgment`, `mechanical`}); the concrete realization is a churning config choice deliberately kept off the locked docs ([D-100](../adr/0100-decouple-the-locked-agent-grammar-from-the-model-landscape-m.md)). Three threads live here until they settle: **(a) current realization binding** — v1's working default is a **uniform high-quality model floor** (Opus-class as of 2026-05-28) with the `mechanical` worker tier run at **lower `effort`** (and/or a lower-cost model) via a worker persona file or session config, and the `judgment` tier (reviewers, orchestrator) at default/high; this is a *transient config choice, not a design lock*, re-evaluated each model release (Opus 4.8 shipped today; Mythos is weeks out) — the realization never feeds an operator-facing cost or time figure, which the plan gate refuses to name ([decision 0321](../adr/0321-adopt-the-build-s-refusal-of-fabricated-cost-and-time-estima.md)). **(b) Dynamic-Workflows adoption** — whether/when to adopt Anthropic's **Dynamic Workflows** (research preview) as the parallel-workers coordination substrate on GA, replacing the current Agent-tool + `isolation: worktree` worker mechanism; the design is substrate-agnostic and must *not* hard-depend on the preview ([R12](risks.md)). The preview's context-window-isolation mechanism *is* documented in primary Anthropic docs; only its deterministic-workflow-file **filename** is secondary-source and uncorroborated — confirm against GA documentation before any adoption. **(c) `model-tier` rename** — the field keeps the name `model-tier` though its members are now demand levels; "tier" still connotes a model ladder, so a rename (high propagation to [agents](../spec/systems/surfaces/agents.md), [glossary](glossary.md), [audits](../spec/systems/guardrails/audits.md), [D-057](../adr/0057-lock-the-agents-surface-wave-1-four-settled-design-forks.md)/[D-100](../adr/0100-decouple-the-locked-agent-grammar-from-the-model-landscape-m.md)) is a candidate for a future pass. *This is the only doc that names today's models, effort levels, and the preview feature — they churn, and the relevant threads are deleted on resolution; durable docs name only the demand tier and the swappable realization seam.*

- **Q31 — A standing in-repo engine-self-conformance instrument, post-v1.** The build-conformance review is maintainer-layer construction tooling that **retires at v1**, and the deployed engine's own `design-review`/`qa-review` lenses are **product-aimed** (they consume a [product-design](../spec/modules/product-design.md) spec referent and are a disclosed no-op for a spec-less engine self-build, [build-orchestration](../spec/systems/lifecycle/build-orchestration.md)). So once v1 ships, when the engine **remediates or upgrades itself** (editing engine *content* per the [remediation loop](../architecture.md#the-detect-to-remediate-loop)), no AI cross-check verifies that change against the engine's *own* shipped design the way build-conformance verified construction. The human merge gate persists (the maintainer's; the [engine-mechanic](../spec/systems/lifecycle/external-contribution.md)'s trust base is the same ratification gate, [D-103](../adr/0103-cross-repo-design-cold-audit-resolutions-engine-clean-branch.md)) — so this is a **handoff of the human gate, not an orphaned one** — but the *AI cross-check* layer beneath it has no post-v1 home. Decide whether a standing deployed/in-repo self-conformance instrument is warranted (an analog of build-conformance pointed at the engine's shipped docs) and who owns it. [audits](../spec/systems/guardrails/audits.md) is the nearest rung, and [D-296](../adr/0296-litigate-engine-template-427-residual-three-l1-l2-l3-audits.md) **narrows** this: audits now carries a standing **product**-spec-conformance sweep (conditional on a `locked` `docs/spec/`), so the old obstacle — "audits only probes accumulated local state, not conformance-to-design" — is gone, and that sweep is the **mechanism template** (cron-fired, read-only, matrix-denominated forward divergence-hunt over locked rows). But it is *product*-aimed and a disclosed no-op on the spec-less **engine self-build**, so it does **not** resolve this question — the genuine residual, a standing AI cross-check of an engine self-edit against the engine's *own* shipped design (the eADR canon, [§18](../principles.md)), stays open. Distinct from [R14](risks.md) (the mechanic path shipping un-exercised) and the pre-release acceptance benchmark ([D-152](../adr/0152-resolve-q15-author-the-pre-release-acceptance-benchmark-the.md)): this is a *standing runtime check after release*. Out of scope for the bootstrap trust-model pass that opened it ([D-136](../adr/0136-re-base-the-bootstrap-trust-model-on-a-sole-non-engineer-gat.md)). The foundational eADR canon ([D-169](../adr/0169-add-the-foundational-eadr-canon-the-engine-ships-its-own-why.md)) now supplies the **shipped design rationale** such an instrument would check against — closing the "no substrate to check against" gap — but does not decide whether the standing instrument is warranted or who owns it. **Concrete evidence for the sizing call ([D-309](../adr/0309-litigate-the-grammar-and-boot-cluster-ledger-grammar-core-u0.md)'s canon truth sweep):** all **33** shipped eADRs were verified against the build; of **12** genuine absolute/mechanism claims, **10 TRUE, 1 FALSE (`eADR-0016`), 1 OVERCLAIMED (`eADR-0024`)**. The canon's default posture is already **honest tiering** — several records volunteer their own fail-open bounds unprompted, and the build ships a hard CI checker-of-checkers enforcing `eADR-0006`'s law. So the drift this instrument would catch is **narrow and one-directional: docs over-claiming, never mechanisms missing** — and it is caught today by the cold-session design audit at the merge, which is exactly where the D-309 pass's own three over-claims were caught. That bounds what a standing instrument would add (a *cadence* over an already-honest corpus, not a missing capability) and argues against sizing it large; it does **not** decide whether it is warranted or who owns it. The standing **negative-fixture meta-check** ([D-256](../adr/0256-authorize-the-every-hard-check-is-proven-to-bite-re-litigati.md)…[D-260](../adr/0260-resolve-re-lock-core-the-dispatcher-run-one-rule-entry-point.md)) likewise supplies the **mechanical** floor of post-release self-conformance — *do the engine's own guardrails still fire?* — CI-enforced, surviving v1, no AI in the loop; it **narrows** this question to its genuine residual, the standing **AI conformance-to-design** cross-check (which the meta-check does not perform), without deciding whether that instrument is warranted or who owns it. That stays open here.
- **Q37 — A post-v1 optional "hackathon" module: a product-aimed divergent-exploration organ on the multi-agent workflow substrate.** The Engine has two organs — one that *executes a known intent faithfully* ([build-orchestration](../spec/systems/lifecycle/build-orchestration.md)) and one that *watches itself for drift* ([telemetry](../spec/systems/guardrails/telemetry.md)/[audits](../spec/systems/guardrails/audits.md)) — but **none that generates and triages candidate intents.** This parks an optional, **leaf** add-on module ([§12](../principles.md) — off the required spine; nothing depends on it) that uses Claude Code's multi-agent **workflow** substrate to run a "hackathon" against the **product** ([§13](../principles.md) — the Engine is a contributor; the subject is the product, the Engine itself only in the [engine-mechanic](glossary.md) reflexive case). **Settled shape ([D-173](../adr/0173-open-q37-a-post-v1-optional-hackathon-divergent-exploration.md)):** *diverge* into many **product-context-grounded** ideas (seeded across themes for coverage/dedup) → vet each through an **independent** adversarial/feasibility/utility **gauntlet** (the cold-session design audit/[design-review](../spec/modules/design-review.md) lens pattern turned generative — independence is load-bearing, consensus is the enemy of evaluation) → *rank* → elaborate the leaders into **rough, product-tailored starting specs** → optionally feed [product-design](../spec/modules/product-design.md) (features) or the product backlog (bugs). **No building; the terminus is starting specs** (the artifact the spec→build chain consumes; a prototype would only yield a half-signal that still needs a full spec). A single operator-facing **depth scale** is set at kickoff — the [build-orchestration](../spec/systems/lifecycle/build-orchestration.md) plan-gate risk-assessment pattern (scope → depth → consent — never a cost or time figure, [decision 0321](../adr/0321-adopt-the-build-s-refusal-of-fabricated-cost-and-time-estima.md)), *all* settled before the run because the unattended "sleep-and-wake" deep run is [routine](../spec/systems/lifecycle/modes.md) mode and headless workflows cannot prompt mid-run — from shallow (ranked raw ideas, operator picks the finalists) to deep (leaders auto-elaborated, unattended), realizable via the workflow runtime's token-budget primitive. **Open sub-threads for the post-v1 design session:** **(a)** the *competitor output-contract altitude* — thick enough that feasibility can be judged honestly, thin enough that it is not a half-spec; **(b)** the *diversity/theme-seeding + dedup* mechanism (multi-modal-sweep / loop-until-dry); **(c)** *one module with pre-tuned target templates* (a target = {scope to scan, competitor output-contract, judging rubric, output routing}) **vs.** a family of thin modules over a shared engine across the [SDLC categories](module-catalog.md) (feature-extrapolation is Product Management, bug-hunt is Verification & Validation) — leaf-ness makes this a no-redesign split either way; **(d)** the operator-facing naming/framing (the [operator-communication law](glossary.md)); **(e)** substrate-availability detection + **degrade-and-disclose** when the workflow feature is absent; **(f)** the *trust bound* — value and feasibility-honesty both scale with the richness of the Engine's product context, so the slate sits in the disclosed-degradation family and must not over-promise (bounded AI judgment, [§17](../principles.md)). **Substrate + the teams restraint:** the substrate is Claude Code's **Dynamic Workflows** (research preview as of 2026-06-05; Claude Code ≥ v2.1.154, paid plans), and **optionality is precisely what licenses depending on a preview** where core may not ([Q21](open-questions.md) (b) / [R12](risks.md) forbid the *core* build-orchestration from hard-depending on it). The platform's collaborative-team machinery (**Agent Teams**, experimental — cannot nest, one-team-at-a-time) is too fragile to bank on, but its existence signals the direction; so keep teams a **design-restraint, not a built feature** — do not bake in "one competitor = one agent," leaving room for a collaborative-team realization on the *generation* side only (the gauntlet stays independent permanently). Design-for-don't-depend, [R12](risks.md) one level deeper. **Post-v1, non-gating for the current build** (rides a preview substrate, adds no v1 capability, touches no locked doc). *This and [D-173](../adr/0173-open-q37-a-post-v1-optional-hackathon-divergent-exploration.md) are the only docs that name today's preview features and versions — they churn, and this entry is deleted on resolution; durable docs name only the swappable substrate seam.*

- **Q40 — Should a declined large erasure batch re-propose its remainder, or stay permanent-decline?** The Layer-2 erasure grammar ([memory](../spec/systems/cognitive/memory.md), [D-285](../adr/0285-litigate-engine-template-363-the-layer-2-erasure-grammar-was.md)) lets one merged single-purpose PR erase a **batch** of records, and consent is to the whole enumerated set — merge erases all, decline (closing the PR) keeps all. As built, a declined batch's records are **not re-proposed**, so an operator who wants to keep one note must forgo erasing the rest. That all-or-nothing decline is fine for today's rare, small, homogeneous crash-duplicate batches, but the **consolidated-raw reclamation** slice will produce large heterogeneous batches where forgoing the whole set to keep one note is a real consent cost. Decide whether a closed large batch **re-proposes its non-kept remainder** (partial-keep) or stays permanent-decline — a consent-model decision, not a grammar change; no new grammar lands until it is decided. **Trigger:** the consolidated-raw reclamation slice. Distinct from the erasure *grammar* (settled, [D-285](../adr/0285-litigate-engine-template-363-the-layer-2-erasure-grammar-was.md)) — this is the *decline consent model* over that grammar.
